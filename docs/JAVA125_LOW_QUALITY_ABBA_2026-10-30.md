# Java Minecraft 1.2.5：ARM／RasterIX 最低画质对照

2026-10-30，按“继续优化帧率，先尝试画质全低”的要求，在 AXU3EG 上完成四轮原版 Java 游戏实测、完整证据回读与独立验收。

**结果：原设置加权 22.8865 FPS，最低画质加权 23.3751 FPS，观测差 +2.13%。两组范围重叠，轮次波动大于平均差，尚不能认定为稳定提速。降低这几项画质没有解决当前卡顿，也没有达到稳定 32／60 FPS。** 未将最低画质推广成默认配置。

## 路线与设置

继续使用 ARM 游戏逻辑、顶点变换、裁剪和命令准备，PL RasterIX 负责光栅、双纹理、深度和混合。没有接入 Vortex、完整 HLS 几何前端或 Mali 渲染。

两组都在预热开始、计数开始和结束时读取游戏对象的十二项实际设置，不能只凭 `options.txt` 宣称生效。原设置已经很低，本次额外降低的是 AO、粒子和晃动；没有降低分辨率或换成低清纹理包。

使用同一个 ARM 共享库 `8e89c36f66e497f26044c779551e5703fbbb7a1a02ff938c76315d8c99d4a993`，匹配双 TMU 位流 `14fd58da8a1a0348b0033f7efef35dc5498c2f4bd1f2a3c43b77404adc9cd961`。FPGA 几何、批次缓存旁路、纹理等待后移三个实验开关均为 0。CPU 前后读数均为 userspace、1,066,666 kHz；没有修改时钟。这是前后读数，不是连续频率记录。

## 对后续优化的判断

本次结果不支持继续依靠 AO、粒子和晃动开关获得大幅提速。两组差约 0.49 FPS，最低组自身相差约 1.64 FPS。不能将 +2.13% 当作已确认的优化收益。

按最低组平均值换算，目前每帧约 42.78 ms；平均达到 32 FPS 需要降至 31.25 ms，减少约 11.53 ms，约 27%；60 FPS 则需降至 16.67 ms，减少约 61%。这只是帧预算，尚未证明能实现，更没有证明长期稳定性。

较值得继续检查的是每帧几何与命令工作量，以及命令供给和 PL 反压。此次最忙线程约占单核 68.0～69.9%，DMA FINISH 等待比约 27.0～27.9%。CPU 与 GPU 可以重叠，DMA 等待不是独占的 PL 光栅时间；这些数据不能单独证明瓶颈只在 ARM 或只在 FPGA。

下一轮应优先记录额外命令来自哪些绘制、批次和图元，并补充命令输入空泡、光栅反压、有效片段等计数，再针对热点优化连续顶点处理、重复几何和批量命令生成。此前旁路与缓存采用不同环境开关，历史 25～26 FPS 也不是本次缓存开启对照的直接基线；不能混在一起声称升降幅度。

最低画质配置和复现脚本已保留，原默认选项已恢复。考虑到目前收益不可靠，不值得仅为这组数据永久降低画质。
