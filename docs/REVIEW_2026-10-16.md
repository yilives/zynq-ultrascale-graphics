# RasterIX Linux 方案审核记录（2026-10-16）

审核结论：本项目是 PS/Linux 与 PL RasterIX 协同方案，必须加载 FPGA bitstream。现有启动包已包含 PL 配置，但发现两个运行阻断问题，当前镜像不应视为已经具备上板运行验收条件。本次仅新增审核记录，未修复实现、未重新构建、未写入 SD/QSPI、未操作开发板。

**FPGA 是否需要烧录**

- `build/boot.bif:5` 明确包含 `[destination_device=pl] .../rasterix_linux.bit`；`scripts/package_boot.ps1:24` 生成同一分区。
- `report/bootgen_read.log:89` 起实际解析出 `rasterix_linux.bit.0`，目标为 PL，owner 为 efsbl；本次另解析真实 BOOT.BIN，确认 PL payload 与当前 bitstream 对应。
- 预期从 SD 启动时，FSBL 自动配置 PL，再进入后续启动阶段。因此不需要每次额外用 Vivado/JTAG 下载，也不要求为此写入 QSPI；FPGA 逻辑仍必须在每次冷启动时被配置。
- PS 运行游戏、GL 状态与顶点处理；PL 运行光栅、纹理、深度、混合、帧搬运和 LCD 输出。`generated/rasterix_config.cmake:22` 关闭软件渲染，没有纯 CPU 回退路径。
- 原厂 Linux 镜像不具有本次硬件和 `0x60000000` 起 32 MiB 的新图形保留区，不能只复制游戏程序到原厂系统来运行本方案。

机制参考：[AMD Zynq UltraScale+ MPSoC Boot and Configuration](https://docs.amd.com/r/en-US/ug1283-bootgen-user-guide/Zynq-UltraScale-MPSoC-Boot-and-Configuration)。

**P1：启动包中的 U-Boot 缺少控制设备树**

位置：`scripts/build_uboot.sh:18`、`:29`、`:33`，`scripts/package_boot.ps1:26`。

脚本启用 `OF_SEPARATE`，却把构建目录中的原始 `u-boot` ELF 复制并改名为 `u-boot.elf`。此 ELF 不包含拼接在 `u-boot.bin` 尾部的控制 DTB。Bootgen 按 ELF 的加载段打包，因此 DTB 丢失。

本次直接读取现有二进制得到：

```text
u-boot.elf PT_LOAD 地址       = 0x08000000
PT_LOAD 文件/内存长度        = 1608424 字节
PT_LOAD 结束地址 / _end      = 0x08188ae8
u-boot.elf 内完整 DTB         = 不存在
u-boot.bin 长度              = 1638124 字节
u-boot.bin 中完整 DTB 偏移    = 1608424
完整 DTB 长度                = 29700 字节
BOOT.BIN 的 U-Boot 分区      = 原 ELF 的 PT_LOAD 内容，没有控制 DTB
```

固定上游归档 `u-boot-xlnx-2026.1.tar.gz` 中，`lib/fdtdec.c:1248` 起的 `fdt_find_separate()` 从 `_end` 找控制 DTB，`:1806` 选择该路径。当前 `.config` 启用 OF_CONTROL/OF_SEPARATE，关闭 OF_BOARD/BLOBLIST，默认环境没有 fdtcontroladdr 覆盖。此处在执行 boot.cmd 前进行，因此 SD 上用于 Linux 的 system.dtb 不能补救 U-Boot 的早期初始化。

修复建议：使用固定上游 `Makefile:1942` 提供的 `u-boot.elf` 目标，它从包含 DTB 的 u-boot.bin 封装 ELF；显式构建并复制这个目标，而不是仅把原始 u-boot 改名。重新生成 BOOT.BIN 和 SD 镜像，增加对最终 ELF/BOOT.BIN 加载内容中控制 DTB 的验证。实际冷启动报错仍须串口确认，本次没有启动新镜像。

参考：[U-Boot Devicetree Control](https://docs.u-boot.org/en/stable/develop/devicetree/control.html)。

**P1：DMA TX 缓冲数量不足，游戏与 smoke 初始化失败**

位置：`linux/include/dma-proxy.h:8`、`config/rasterix_axu3eg.json` 的 dma.buffer_count、`src/ps/DMAProxyBusConnector.cpp:76`。

当前 BUFFER_COUNT=4。实际 400×240 配置和 32768 像素内部缓冲经 `external/tuxracer/RasterIX/lib/gl/RenderConfigs.hpp:55` 的公式得到 3 个分片。`ThreadedVertexTransformer.hpp:143` 为每个分片申请两个命令缓冲，依次申请索引 0～5；连接器遇到索引 4 即抛出 `TX buffer index`。

`external/tuxracer/winsys.cpp:81` 起的全局 guard 会在 main 前构造该对象；`samples/rix_smoke.cpp:55` 同样会触发。因此即使驱动、DMA、PL 全部正常，游戏仍无法进入菜单，smoke 也不能完成绘制测试。

按实际文件参数执行原索引公式的只读最小检查结果：

```text
display_slices          = 3
display_tx_indices      = [0, 1, 2, 3, 4, 5]
tx_buffer_count         = 4
reserved_store_index    = 3
first_throw_index       = 4
minimum_tx_buffer_count = 7
```

修复建议：至少提供 7 个 TX 缓冲，6 个用于分片双缓冲、1 个用于 DDU STORE。只提高到 6 仍与最后一个资源上传槽冲突。统一修改共同配置、ABI 头文件和所有实际副本，重新生成配置并重编匹配的驱动、用户态、smoke 和镜像；按共同配置摘要更新规则重建对应硬件。增加实际构造链检查，并在初始化前验证所需缓冲数。

**P2：发布门禁缺少当前源码到硬件产物的关联检查**

`build_local.ps1:13` 只在显式指定 RebuildHardware 时重建硬件；默认路径检查并复用旧 XSA 和 routed checkpoint。`scripts/release_manifest.py:25` 起核对产物摘要、共同配置和已有报告，但没有记录并比较完整 RTL/XDC/补丁/工具输入到 bitstream 的构建快照。

触发条件：修改 RTL 或约束但不改变配置摘要，再执行默认本地构建。旧硬件仍可能通过产物之间的一致性检查。此项不表示本次已经证实 bitstream 与源码不同；它表示现有门禁不能证明二者对应。

修复建议：生成覆盖全部硬件输入的构建摘要，并在复用硬件时强制核对；不匹配时要求重新实现。目前修改硬件后应显式使用 RebuildHardware。

**尚未完成的验收**

- `docs/FACTORY_IMAGE_INSPECTION_2026-10-16.md` 的 COM11 记录验证的是厂商原 SD 系统，不能计入新 RasterIX 镜像的启动、GPU、LCD 或性能验收。
