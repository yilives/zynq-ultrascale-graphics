# Java 1.2.5 ARM／DMA 瓶颈定位实测

2026-10-31，R134 诊断、R135 证据回读。实测支持优先优化 ARM 的几何与命令准备链路；**仍未证明 DMA 硬件带宽已经饱和**。

## 运行条件与结果

保持当前选择的原画质：Tiny／Fast／关闭云，AO 开启、全部粒子、行走晃动；400×240、256 纹理、双 TMU；最近邻输出，FSR／CNN 关闭。ARM 游戏逻辑和几何前端 → DMA → PL RasterIX 像素后端。

同一保存世界，热身 60 秒，正式呈现计数窗口 31.007189 秒完成 772 帧，诊断运行 **24.90 FPS**。计时器、日志开销尚未校正，该轮明确标记 `accepted_performance_run=false`，不能据此宣称新的优化收益，也不能将它与历史 25～26 FPS 的差直接归因于计时开销。

独立回读与全部原有正确性门槛通过；与 R131 的 48 个原生像素结果逐字节比较，合计 18,432,000 字节一致；游戏画面 SHA 也相同。玩家位置、视角和世界类型保持不变，生命值为 20。没有发生 GPU 分区溢出。

## 阶段计时

以下为同一内部计时窗口 31.052616 秒内的完成范围累计。CPU 比例以一个 CPU 核为 100%。这些范围有嵌套，多个线程也会同时工作，**各行不能相加**，不能当作互斥的整帧耗时拆分。

| 测量范围 | 墙钟累计／窗口 | 线程 CPU 累计／窗口 | 调用数 |
|---|---:|---:|---:|
| 几何工作线程总范围 | 68.11% | 64.47% | 1,546 |
| 顶点批次链路 | 58.49% | 58.38% | 18,556 |
| 前端等待几何线程 | 53.68% | 1.40% | 361,561 |
| 等待上传线程 | 17.16% | 0.04% | 2,319 |
| 纹理上传函数 | 7.43% | 3.81% | 1,546 |
| 命令上传任务 | 19.85% | 0.38% | 1,546 |
| TX START 局部范围 | 0.49% | 0.41% | 15,200 |
| 命令流 FINISH 等待 | 23.54% | 0.14% | 4,638 |
| 资源 STORE FINISH 等待 | 4.75% | 0.35% | 10,562 |

“顶点批次链路”包含顶点读取、变换、裁剪、三角形参数准备和命令封装；当前没有把这些子步骤分别计时。其墙钟与 CPU 时间接近，支持该范围主要在执行计算。该范围占几何线程 CPU 时间的 **90.5%**。前端等待几何线程的墙钟累计较高，也支持继续检查生产端串行依赖。

命令流完成等待主要为睡眠等待；它可能受到 FPGA 接收反压、DDR 访问、中断与调度影响，不能归为纯 DMA 搬运时间。资源上传完成等待单独约 4.7%，因此将整个等待比例归因于纹理传输也不成立。

原有 DMA 统计窗口的业务吞吐约 **30.86 MiB/s**。这是业务负载的平均有效字节率，没有测到物理 DMA 上限。命令流从提交到观察到完成累计约 85.2%，其中到调用 FINISH 前的间隔累计约 61.6%；这两个数包含提交后其他工作、可能已完成而未回收的时间，不能当作 DMA 忙碌率或空闲率。

## 源码语义与下一步

`rix_dma_proxy.c` 中 FINISH 等待 DMA 描述符完成回调。连接器与驱动当前均限制每通道一笔在途传输；七个缓冲槽提供生命周期和准备空间，不代表七笔硬件请求并发。不能直接删除完成等待或仅增加槽数来保证提速。

下一步优先细分批次中的变换、裁剪、三角形参数和封装热点，再以相同画质作对照。若继续排查 DMA／PL，需要增加输入 `TVALID && !TREADY`、无输入以及 FIFO 占用等硬件计数，区分供给不足与下游反压。现有 `gpu_busy_cycles` 来自命令解析器 `state != COMMAND_IN`，也不能替代完整 GPU 利用率或 DMA 反压测量。
