# AXU3EG / RasterIX：从游戏移植到 FPGA FSR 的整体优化过程

初版日期：2026-10-25，更新至2026-10-26。项目：`rasterix-linux`。目标平台：AXU3EG / XCZU3EG。

本文总结本项目从 Linux 启动、游戏渲染、神经风格迁移，到 FPGA FSR 的主要改动、验证方法和取舍。各阶段的构建日志和原始证据保留在专门记录中；本文不将不同游戏、场景、时间窗或画质的数字拼接成严格加速比。

**当前主目标：ClassiCube 保持 64³ 世界、32 格视距、400×240 源渲染、800×480 输出，运行完整 FPGA FSR，继续争取稳定 60 个新画面/秒。** 视距 16 的结果仅用于探查性能上限，不作为视距 32 达标。

## 1. 当前已做到什么

| 项目 | 已验证结果 | 边界 |
|---|---|---|
| Linux 与 RasterIX 游戏 | 已真实启动、LCD 出图，多游戏可运行 | 实体键鼠手感、全部游戏长时间稳定性仍需单独验收 |
| ClassiCube | Classic 方块世界、移动、挖放、菜单、存档、重载；ARM 逻辑/顶点前端，FPGA 像素渲染 | 不是 Minecraft Java 生存版 |
| 神经风格迁移 | 已训练的三层 INT8 CNN 在 FPGA 推理，油画/动漫可选 | 小网络原型，不能等同完整教师；本次 FSR 60 FPS 测试未串入 CNN |
| 完整 FPGA FSR | EASU12 + RCAS5，400×240 → 800×480，实时路径 ARM 不计算超分像素 | 固定 2×、定点实现；无神经超分模型 |
| 原v23推荐入口的视距32长测 | 两轮各120秒，FSR **57.089 FPS**，源 **57.107 FPS** | 严格稳定60尚未达到；各轮结果按各自对照解读 |
| v26可选向量优化 | 四轮各120秒交叉对照，候选FSR **58.194 FPS**，同组原版56.834 | 平均提高2.39%，p99变差，保留实验入口 |
| 视距 16 性能对照 | 两轮各 120 秒，FSR **60.106 FPS** | 减少可见距离；仍有一次略超门槛的间隔，不能算视距 32 或严格稳定 60 达标 |

当前板上为 v23 RAM 位流，独立键鼠 FSR 入口已部署到 `/tmp`；本轮没有更新 SD 启动镜像。断电重启后，需要重新执行匹配的位流加载与文件部署流程。

## 2. 先建立完整链路，再逐段找瓶颈

当前无神经风格的 FSR 链路为：

```text
ARM A53 / Linux
  ClassiCube：输入、世界、物理、区块网格、可见性
  RasterIX 软件前端：GL 状态、顶点读取/变换、裁剪、三角形设置
       ↓ 后台命令列表、DMA
FPGA RasterIX
  光栅化、纹理、深度、混合 → 400×240 RGB565 源帧
       ↓ 帧复制桥 / SNP1 独立快照
FPGA FSR
  LOAD：将受保护输入装入片内缓存
  COMPUTE：完整 EASU12 + RCAS5 → 800×480 高分辨率非活动槽
       ↓ 最后 AXI B 完成、帧标记核验、POST 换页确认
FPGA 显示扫描 → 800×480 RGB LCD
```

ARM 管理缓冲所有权和任务调度。FSR 的 LOAD、滤波和结果写回由 PL 完成。游戏顶点前端仍在 ARM，不能将当前系统描述为“所有游戏渲染步骤均在 FPGA”。

性能关注点随优化不断转移：最初是系统根本不能启动，随后是游戏适配与串行等待，再是神经处理的搬运，之后是 FSR 算术和缓存，最后逐渐回到游戏源渲染与换帧节奏。

## 3. 第一阶段：修复启动、DMA 和可见画面

### 3.1 U-Boot 控制设备树

最初把原始 `u-boot` ELF 当作可直接打包的启动载荷，遗漏 OF_SEPARATE 控制 DTB。Linux 的 `system.dtb` 无法补足 U-Boot 自己启动所需的控制树。修复为构建和打包含完整 `u-boot.bin` 的 `u-boot.elf`，检查实际 ELF PT_LOAD 字节与 BOOT.BIN 分区内容。

后续针对实际 BL31 后停住的现象完成启动包修复、SD 文件更新与回读，最终用户确认 Linux 成功启动并出现游戏画面。这里采用真实启动与读回结果收敛问题，没有把本地“打包成功”当作冷启动成功。

### 3.2 DMA 缓冲和退出生命期

三片区双缓冲需要六个 TX 槽，资源上传还需要独立槽。最初四槽配置会导致初始化时的索引异常。最终统一 ABI 2、每方向八个 1 MiB 槽，显示列表使用 TX 0–5，资源暂存使用 TX 7，TX 6 保留；构建与初始化均检查最低容量。

同时把大型渲染对象移到堆上，确保渲染器、命令存储和纹理在顶点线程、上传线程、DMA 及最终呈现全部结束后才销毁。后续所有并行优化都以这些所有权边界为前提。

### 3.3 LCD 比例与实际呈现

完成 400×240 → 800×480 全屏布局与文字可见性核对，修正了画面比例问题。实际 PS 串口为 COM11，COM15 为后来接入的 PL 串口。MiniDP 属于另一条 PS 显示路径，当前游戏输出仍为 RGB LCD，不能因为存在 DP 驱动就认为游戏已通过 DP 输出。

来源：[阻断修复](BLOCKER_FIX_2026-10-16.md)、[启动修复](BOOT_FIX_2026-10-16.md)、[LCD 布局](LCD_LAYOUT_2026-10-18.md)、[比赛与 DP](RACE_AND_DP_2026-10-18.md)。

## 4. 第二阶段：多游戏适配与 ARM 图形前端

接入 Tux Racer、Neverball、Neverputt、Quake I、Quake III，并探索东方类游戏与批量精灵。主要工作包括固定功能 GL/VBO 适配、纹理容量约束、六平面裁剪、输入与退出、持久配置和按引擎选择呈现策略。

一项有效改动是 draw 内的索引顶点缓存和更大的变换缓存。Neverball 典型索引命中率约 68.4%，同轮记录从 21.77 到 28.50 FPS；Quake I 从 28.38 到 30.04 FPS。其他游戏接近持平，未把小幅波动认定为收益。

曾尝试全局同步，部分游戏反而降至约 15–24 FPS，因此最终按游戏保留合适的提交方式。这个阶段的经验是：**减少等待必须结合真实缓冲复用关系，不能给所有引擎套同一种同步策略。**

东方部分实际接入了 TH06 开源便携引擎和官方《东方红魔乡》0.13 体验版数据，包含 ANM/ECL、原作弹幕与关卡逻辑。修正呈现后重复限帧的问题，逻辑保持约60 Hz，首版渲染约29.94 FPS。之后用透明边缘预滤波和128×128纹理分页改善图集细节；balanced 模式同区间约28.99 FPS，原图native约18.86 FPS，因此默认选择平衡画质。独立批量精灵样例与实际TH06引擎分别验收，没有把样例性能当作完整游戏性能。

触摸则通过GPIO模拟I²C接入GT911，打通evdev和Xorg libinput。控制器识别、自动加载及虚拟输入链路通过，实际手指四角方向和操作手感仍待验收。这些接口工作与FSR性能分开记录。

ClassiCube 的主要优化依次为：

| 改动 | 原因与结果 |
|---|---|
| 方块面四边形提交 | 默认独立面由六次索引顶点处理降为四顶点路径；短/长测约提升 11.4%。两种三角剖分有极少像素差异，因此没有宣称逐位等价 |
| 正确客户区与菜单指针 | X11 客户区保持实际 400×240；在游戏画面内画指针，使 FPGA 扫描的 LCD 也能看到菜单鼠标 |
| 异步前台/顶点/DMA 流水 | 去掉每帧额外的全队列排空，保留复用前等待与退出 fence；复杂路线长测约 42.19 → 57.31 FPS |
| 提交上限 120 | 减少软件限帧与约 60 Hz 显示相互阻塞；120 是提交上限，不是 LCD 输出 120 FPS |
| 专用 PackedVertexReader | 一次检查后读取 float3 / ubyte4 / float2 常用格式，减少通用属性转换；前台约 7.0 → 3.1 ms，高视距累计 CPU 用时约降低 18.7%，显示帧率基本持平 |

专用读取器保留步长、偏移、禁用属性与其他格式回退；没有用 fast-math 换精度。实际有效顶点字段逐位对照约 1,157 万个顶点通过。源取帧还修正了“软件以为的 front 指针”不一定等于 LCD 正在显示的帧的问题：后续验收只在队列排空且硬件帧号稳定后读取真正选中的源。

来源：[多游戏优化](GAME_OPTIMIZATION_2026-10-19.md)、[TH06接入](TOUHOU_2026-10-19.md)、[TH06画质优化](TOUHOU_OPTIMIZATION_2026-10-19.md)、[触摸与早期后处理](POSTPROC_TOUCH_2026-10-18.md)、[ClassiCube 初版](CLASSICUBE_2026-10-21.md)、[异步提交](CLASSICUBE_PERFORMANCE_2026-10-21.md)、[专用顶点读取](CLASSICUBE_VERTEX_2026-10-21.md)。

## 5. 第三阶段：把真正的神经风格网络接入 FPGA

最初的 poster、sepia、binary 是固定颜色算法。用户明确需要风格迁移网络后，采用 PC 完整教师网络产生样本，再训练固定画风的小型学生网络。

学生为 **160×96，Conv3×3：3→8→8→3，两个 ReLU，INT8**。硬件实现完整卷积、偏置、舍入、饱和及边界复制；油画和动漫使用独立训练权重。完整教师有大量卷积与全局归一化，当前器件无法直接按原网络规模和游戏目标帧率部署。

主要优化沿着“核心算得快，但整链路仍慢”的原因逐层展开：

| 阶段 | 改动 | 实际证据/结果 |
|---|---|---|
| 首版 A53 实时链路 | 软件定点 CNN 与取帧、放大 | Neverball 两风格约 3.8–4.0 FPS，作为历史起点 |
| 首版 FPGA CNN + 传输 | 卷积硬件化 | 部分实时阶段约 8.5 FPS；PIO/取帧仍占显著时间 |
| 四核取帧与 NEON | 划分源行、精确 SIMD 缩放 | 约 12 FPS，正式连续测量约 12.06 FPS |
| NNS2 核心流水 | READ/MULT/REDUCE/ACCUM 重叠 | 1,843,200 → 414,738 周期，名义 100 MHz 核心 18.432 → 4.147 ms |
| 先风格化、后 PL 放大 | 只写回 160×96，FPGA 五倍双线性 | 每帧显示写入 1,536,000 → 61,440 B；放大不是神经超分或 FSR |
| DDR 返回突发缓存 | 不让慢像素消费者一直占住 DDR R 通道 | 修复“核心提速但整体变慢”的回退，正式入口阶段约 23.79 FPS |
| 帧复制桥突发化 | 16-beat 读取缓存后分别写显示/快照 | COPYING→READY 单次样本 25.562 → 2.358 ms；Neverball 正式动漫约 28.44 FPS |
| MC 专用调度/残差风格 | 原分辨率细节加低分辨率神经残差、HUD 保护、源提交节流 | 同模型 ABBA 20.665 → 24.199 FPS；不同场景长测单列 |
| MC 模型质量 v5 | 复活两个零通道、量化感知训练、上下文/运动约束 | 新留出八帧对教师融合参考 MAE 4.0520 → 2.3271；实际约 25.68 FPS |

这些数字来自不同阶段和部分不同场景，不能逐项相乘。核心 4.147 ms 不代表系统约 241 FPS。模型质量误差也不等于主观画质：学生只有 7×7 感受野，油画新候选在开发路线退步，因此保留旧油画模型；运动一致性仍有未解决的问题。

来源：[神经风格总记录](NEURAL_STYLE_2026-10-20.md)、[并行取帧](NEURAL_STYLE_PARALLEL_2026-10-20.md)、[CNN 流水和 PL 放大](NEURAL_STYLE_FPGA_PIPELINE_2026-10-20.md)、[突发复制桥](NEURAL_STYLE_COPY_BURST_2026-10-20.md)、[MC 调度](CLASSICUBE_STYLE_OPTIMIZATION_2026-10-22.md)、[模型 v5](CLASSICUBE_MODEL_QUALITY_V5_2026-10-23.md)。

## 6. 第四阶段：FSR 从 ARM 参考到完整 FPGA 实现

### 6.1 明确算法和性能口径

最初比较 FPGA 最近邻、双线性和 A53 FSR1。固定短窗里游戏源约 60 FPS，A53 完整 FSR 新输出仅 **2.32 FPS**。用户进一步明确希望超分在 FPGA，因此随后迁移完整 FSR1 EASU12 + RCAS5。

Arm ASR 是另一套技术路线；当前只有其官方 API 验证，未形成这里的可用渲染后端。当前 PL FSR 不应叫作 Arm 神经超分。FSR1 自身也不是神经网络，更不是依靠运动向量的 FSR2/3。

### 6.2 先保证数值语义，再优化 HLS

FP32 全尺寸模型与 CPU 参考核对后，因资源约束转向定点。曾出现边缘最大 14/255 的误差，定位为 RGB565 亮度累加的微小舍入梯度被边缘归一化放大。修复使用通道 ROM、受控整数舍入和更高精度亮度；没有放宽门槛隐藏误差。

之后大部分硬件版本都要求与已接受的 v8 定点金标准逐像素相同。典型完整功能集为 19 张 800×480 输出，共 7,296,000 像素。定点金标准与原浮点算法的允许误差和“后续版本逐字节等于 v8”是两种不同检查。

### 6.3 硬件结构的主要演进

| 阶段 | 发现的瓶颈 | 解决方法与结果 |
|---|---|---|
| v7 → v8 | 每像素单独 AXI 写，AW/B 事务过多 | 行缓存、连续写与适配器突发；静态计算约 230 → 97.6 ms，v8 游戏 FSR约 8.468 FPS |
| v9/v10 | EASU、RCAS、写回串行 | DATAFLOW、行缓冲和 FIFO；调整资源共享使循环可并发，v10 计算实测约 46 ms |
| 运行时重叠/预取 | 算完、等显示、取下一输入串行 | LOAD 与 POST 确认重叠，COMPUTE 期间提前取得下一快照，v10约 18.52 FPS |
| v11–v16 | 循环启动间隔和 RCAS 内联排程 | 64 字预填充写块、按实际依赖调整 II；v16 实测计算约 23.193 ms，新输出约 30.03 FPS |
| v17–v19 | 动态边界地址让 HLS 保守串行读取 | 显式四 bank 窗口、静态编号后旋转选择；EASU/RCAS 达 II4，窄偏移参数回收 DSP，v19计算约 15.494 ms |
| v20/v21 | 升 200 MHz 后整机无法布局 | 两版详细布局失败；未作为可用交付，原失败日志保留 |
| v22 | 需要先腾出扫描器面积才能装下高速核 | 行/奇偶列分组，缩放器独立 LUT 8,810 → 3,978；整机布线通过，FSR200 MHz，实测计算约 8.20 ms |
| v23 | 非 CNN 扫描仍把下游背压传进 DDR R 通道 | 全模式复用突发 BRAM；同调度 LOAD 约 3.613 → 0.793 ms |
| 最新 ahead 调度 | 短计算下请求下一输入还可以更早 | LOAD 释放后立即请求下一 SNP；所有权不变，视距32长测55.00 → 57.09 FPS，长间隔次数减少约69.83% |

v17 仅加 bank 指令仍被动态地址约束，未获得预期 II；显式窗口结构才解决端口供给。v20/v21 的失败也说明“单核综合通过”和“整个 FPGA 可布局、可布线、满足时序”是不同层次。

| 位流 | 普通调度 FSR FPS | 预取 FSR FPS | 预取 LOAD | 预取 COMPUTE |

| v16 | 20.186 | 30.030 | 5.723 ms | 23.193 ms |

| v22 | 30.920 | 44.372 | 3.613 ms | 8.201 ms |

这组数据证明了同一位流内的调度收益，也记录了逐代硬件进展。不同版本之间不是位流随机切换 ABBA，因此不宣称严格隔离了所有环境因素。

### 7.2 覆盖更长路线的最新记录

每组两轮、每轮 120 秒 FSR 窗口，世界和分辨率保持相同；路线随墙钟时间自动转向和移动。

| v23 调度 / 视距 | FSR 新输出 FPS | 游戏源 FPS | >24.948 ms 间隔总数 | 严格稳定60 |
|---|---:|---:|---:|---|
| COMPUTE 起点提前请求 / 32 | 55.000 | 56.882 | 421 | 未通过 |
| COMPUTE 起点提前请求 / 24 | 56.675 | 59.146 | 537 | 未通过 |
| LOAD 后提前请求 / 32 | **57.089** | **57.107** | **127** | 未通过 |
| LOAD 后提前请求 / 16 | 60.106 | 60.127 | 1 | 未通过，且视距不同 |

视距 32 的新调度比上一调度平均提高 **3.80%**，超门槛间隔减少 **69.83%**。不能把短窗 47.83 → 长测 57.09 当作完全相同场景的提速比。

稳定 60 的当前验收条件为：每轮稳态至少 59.8 个独立新帧/秒，且没有超过 24.948 ms 的确认间隔。视距16有一次24.968 ms，虽然只超20 µs，仍按原标准保留不通过。该时间来自 CPU 观察 POST ACK，包含调度和轮询，尚无光学测量。

LCD 像素时钟为 200/6 MHz，总时序1056×525，对应 **60.125060 Hz**。内部处理吞吐超过60不能让这块屏幕显示更多独立刷新帧；重复扫描同一帧也不计作新输出。

## 8. 验证方法也是优化工作的一部分

每次候选按相同顺序推进：

1. **固定身份和场景。** 保存源码、配置、模型、ELF、位流、boot ID 和 SHA；不能把旧运行时随意用于新位流。
2. **先检查功能。** 普通内存数值/边界测试、全尺寸参考图；需要时做缩小 C/RTL、随机背压、取消、错误和负向对照。
3. **整机实现。** 检查布局/布线、最终资源、时序、CDC、实际缓存是否映射 BRAM；HLS 估算不替代整机结果。
4. **RAM 加载并可回退。** 不直接覆盖唯一可启动镜像；加载后核验当前启动绑定的 receipt 和原有 GPU/CNN 接口。
5. **板端全帧与 LCD。** 典型三张完整黄金图共1,152,000像素零差异，再核验LCD6,000采样；GPU旧错误计数不覆盖所有新增FSR主口错误，不能只看计数零。
6. **真实性能对照。** 区分CPU提交、GPU源呈现、FSR完成/POST确认，使用实际帧数与窗口加权；计时阶段不抓图或传输素材。
7. **退出和恢复。** 先排空在途AXI与快照，再释放银行、停游戏、恢复POST与用户配置；超时隔离保留锁，禁止通过强杀伪装成安全退出。
8. **回读独立核验。** 主机重新计算归档SHA、逐项身份、帧计数和间隔，不只信板端最终一句passed。

工程中保留过的失败包括：无真实源帧时的显示欠流、错误front取帧、定点边缘误差、v20/v21布局失败、测试名称超长导致游戏未启动、证据浮点输出精度导致校验器误拒绝。均按具体原因修复并保留原始记录，没有改写失败数据。

## 10. 视距32后续怎么继续

视距32的源帧率57.107与FSR输出57.089已经接近，当前优先级发生了变化：继续单独减少FSR COMPUTE，无法保证源本身低于60时得到60个不同游戏帧。

## 15. 整个过程的核心结论

本项目的优化路径是：**先让系统正确运行 → 找到实际瓶颈 → 消除无效串行与小事务 → 用合适缓存/流水降低核耗时 → 解决整机面积和DDR背压 → 用所有权安全的调度隐藏等待 → 回到源渲染和帧节奏。**

最有价值的进展不只来自增加并行乘法器或提高频率。帧复制突发、扫描缓存的bank布局、切断DDR返回背压、在正确的时刻申请下一帧，都曾比单纯优化算术更有效。当前下一步仍应按测量决定，而不是靠某个单核理论FPS推算全系统性能。
