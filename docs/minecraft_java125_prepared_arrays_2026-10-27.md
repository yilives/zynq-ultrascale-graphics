# 原版 Java：显示列表已解码数组的直接读取实验

> 2026-10-28 配置更正：历史脚本写入了 1.2.5 不读取的 `renderDistance` 键，本文的 Tiny 标注须按归档 `viewDistance` 复核；已确认 R75–R78 实际为 Far。原始计数及同组对照不重写，详见 [Mali 试验及视距核查](MALI_JAVA125_2026-10-28.md)。

2026-10-27。显示列表直接读取已接入并通过实机回归。本组剔除编译线程后的采样窗口 CPU 平均占用由 **1.463 核降至 1.285 核，约 −12.17%**；实际新帧率为 **5.000 → 5.031 FPS**，仅 +0.63%，落在逐轮波动范围内，未确认实质提速。候选保留为可选实验，默认继续使用原 C420 库；本轮仅作 RAM 试验。

## 已实现的路径

原 `OwnedBatch` 在编译显示列表时已把位置、颜色、法线及两个纹理单元坐标解码并保存为 Vec4/Vec3。旧重放将它们包装回 RenderObj，再按类型、长度、步长和索引解析一次。新候选为这类输入增加 `drawObjFetched`，直接从保存的数组构造同格式 VertexParameter。

颜色、法线、点大小或纹理坐标数组未启用时，仍读取**调用时**常量；矩阵、纹理绑定、纹理矩阵、光照、图元和深度/混合状态继续使用原状态设置。每个完整参数仍复制进原 CPU 命令列表，任何数组引用都不传给异步线程，因此不会因删掉或重定义显示列表而留下悬空指针。

没有减少顶点、关闭纹理、改变客户端 JAR、变换算式或线程数据格式。已验收分支原有的打包读取、索引缓存及通用回退代码完整保留；提取共用状态设置后，脚本将回退函数还原并逐文本核对。它仍是 ARM 顶点前端优化，像素由实际双 TMU FPGA 光栅管线生成。

开关为 `RIX_JAVA_PREPARED_ARRAYS=1`；默认关闭。独立候选 SHA-256：`daa1ebb53496e62cf3d75ab351cd60a58b7025e06144c45b41551ae699d30cf9`。没有改动被上一轮否决的向量特殊成员实现。

## 构建与正确性

完整重编译 GL/GLX，核验 542 项源码输入和 116 个新私有头文件使用者，公开 GL 符号相同。实际编译宏为双 TMU、最大纹理 256，关闭软件像素渲染。FPGA 位流与资源没有变化。

主机和 AArch64 的字段测试覆盖 32 种数组开关组合、三组调用时常量、24,672 个输入顶点；位置、颜色、法线、点大小、两组 UV 及 sourceIndex 均与通用读取逐位一致。包含 NaN 负载、负零、无穷及非正规数，摘要均为 `1d5caec9c16d0e9f`。ARM 检查在 R43 的硬件切换前实际执行。

新增真实 FPGA 探针，在同一候选二进制中分别关闭/开启新路径，验证三组 400×240 双纹理色板：双单元相乘、仅 unit0、仅 unit1。编译后改写位置、颜色及 UV 源数组；重放时再改颜色常量、unit1 坐标常量、模型矩阵和纹理矩阵。每模式三幅 RGBA 逐字节相同，同时核验预期色值。候选必须记录正数 fast_vertices，关闭时必须只记录 fallback_vertices。

既有 30 幅原生回归图、原版游戏加载、正常关闭、计数与换页对应、硬件错误以及原配置恢复检查仍保留。没有以图像近似或屏蔽错误使测试通过。

## 需要保留的 R44 失败

R44 的 GPU 探针及原版活动窗口完成，但运行器将新增的单行结束汇总当作周期时间序列，沿用了 `len(rows)>3` 断言，因此原记录是 `passed=false`，随后恢复成功。

统计文件实际有一行，记录 fast_draws=302,322、fast_vertices=107,383,264、fallback_vertices=0。它证明实际进入新路径；不是 JVM 没有运行退出统计。该原因在排查中已纠正。修复只针对新字段：结束汇总要求恰好一条、开关及正数计数匹配；原 DMA/CPU/纹理时间序列仍要求多条记录。渲染二进制没有改动。

R44 原始失败状态和诊断读数保留，不覆盖成成功。修正后使用 R47/R48 新编号重测，未启动的 R45/R46 归档不复用。

## 受控对照方法

采用原 C420 库与候选开关开启作端到端比较，均为原版 Java 1.2.5、400×240、完整 256 纹理、双 TMU、Tiny/Fast、关闭云、精确页去重、最近邻呈现。通过原版 options 统一和平难度，暖机 60 秒，再采集约 31 秒。计数器读取与板侧单调时钟配对，JVM 及父进程退出上限协调为 240 秒。

有效顺序为 **R43 原库、R47 候选、R48 候选、R49 原库**；时间线上 R44 是另列的验收器失败，不隐藏这次中断。每次使用同一冻结世界起点，最终从原始 NBT 核对位置、朝向、生命值和世界时间。两次/库不构成长时间平稳性或 60 Hz 验收。

此前普通难度、10 秒暖机、子进程外围计时得到的 7～8 FPS 不与本组直接计算收益。

| 轮次 | 库 | 完成帧数 | 计数窗口 | FPS | 非编译线程平均 CPU，占一个核的百分比 |
|---|---|---:|---:|---:|---:|
| R43 | 原库 | 147 | 29.996 s | 4.9007 | 145.70% |
| R47 | 直接读取 | 149 | 30.011 s | 4.9649 | 128.22% |
| R48 | 直接读取 | 158 | 31.010 s | 5.0951 | 128.72% |
| R49 | 原库 | 153 | 30.006 s | 5.0989 | 146.86% |

按各组总完成帧数/总时间汇总：原库 **300／60.002 s=4.9998 FPS**，候选 **307／61.021 s=5.0311 FPS**。两次候选结果均与原库范围重叠；样本只有每库两次，没有统计置信区间或长期流畅性结论。

CPU 指标来自进程任务统计，排除名字含 Compiler 的线程，并按 CPU 诊断窗口长度加权。它是这组场景的**平均占用观察**，不是指令数、能耗或函数独占耗时；诊断窗口与 GPU FPS 窗口边界稍有不同。没有调频、能耗或与神经网络并发运行的收益结论。候选下诊断 STREAM 流量约 26.3～26.6 MiB/s，原库约 25.1～25.5 MiB/s，没有以减少实际提交内容换取这组占用读数。

四轮原始 NBT 位置、朝向相同，Health=20、DeathTime=0；R43/R47/R48 最终世界时间为 2279，R49 为 2239，**最终模拟时间没有完全一致**。因此不把这组微小 FPS 差异解释为明确提升。完整数据见[受控汇总](../report/minecraft-java-125/swap-fence/prepared-arrays-comparison/acceptance.json)。

每轮 30 幅原生回归图及新增六幅双模式图均一致，跨另外三轮合计比较 **41,472,000 字节**。候选在同一个二进制中关闭/开启新路径时三幅新图也完全相同；实际游戏的 fast_vertices 为正、fallback_vertices 为零。最大计数器读取跨度约 **0.077 ms**，全部硬件错误为零，原配置和 v23 恢复，SD 未更新。

## 后续瓶颈应如何处理

本候选只删除重复数组解析，仍对每个顶点创建并写入 PushVertexCmd，顶点线程随后逐项拆包和执行原变换。若端到端改善有限，应根据新条件下的 CPU/等待数据决定后续方向，不能仅凭某个函数的样本占比推断整帧提速。

本组 DMA FINISH 等待占诊断窗口约由 22.37% 变为 23.00%，没有随 CPU 占用下降而缩短。它仅代表记录的完成等待时间，不能当成完整 GPU 利用率。下一步应拆分顶点线程的拆包/变换、上传与 GPU 等待，再选择真正限制新帧产出的阶段。

下一项更大的改动可评估“整批已解码顶点提交”：减少逐顶点的封装和拆包，但需把调用时常量、矩阵状态及数据所有权固定到相应队列。数组所有者必须保留到异步线程完成；不能直接把可能被 glDeleteLists 释放的裸指针放入后台队列。该步骤本轮尚未实现，不预估其收益。

构建、单位字段、原生 GPU 探针及证据生成脚本保留在项目内；候选位于 `build/minecraft-java-125/prepared-arrays`，原库位于 `build/minecraft-java-125/texture-shadow`。
