# 原版 Java：新热点采样与顺序批次变换实验

> 2026-10-28 配置更正：历史脚本写入了 1.2.5 不读取的 `renderDistance` 键，本文的 Tiny 标注须按归档 `viewDistance` 复核；已确认 R75–R78 实际为 Far。原始计数及同组对照不重写，详见 [Mali 试验及视距核查](MALI_JAVA125_2026-10-28.md)。

2026-10-28。本轮同一二进制连续四轮 ABBA：原缓存加权 **4.5271 FPS → 顺序批次专用入口 4.8874 FPS，观察增益 7.96%**。改动去掉已展开批次中的无效变换缓存维护及相关临时搬运。仍未达到流畅运行；只作为有收益的实验候选保留，未更新 SD 或设为默认。

此前整批提交约 4.4 FPS，本轮先对该 v4 库重新采样，再定位下一项开销；没有用采样轮的 FPS 代替对照基线。

## 采样确认了什么

R70 使用已验收 v4 库，原版 Minecraft Java 1.2.5、400×240、双 TMU、完整 256 纹理、和平难度及 60 秒暖机。之后进行约 17 秒用户态 CPU-clock IP 采样，周期 2 ms，共 8,775 个样本，lost/dropped/corrupt 均为零。采样过程不发送信号、不操作 GPU；R70 的 FPS 仅作诊断，明确排除出性能对照。

未裁剪 ELF 经同版 strip 后与板上 `6fae946e…` 库完全一致，函数地址用该 ELF 解析。两个同名线程通过实际符号区分，未依据 Linux comm 名称直接指定角色。

| 原生几何线程热点 | 占该线程 CPU 样本 |
|---|---:|
| Vec4 复制赋值 | 13.78% |
| Vec4 const 右值赋值 | 7.01% |
| Mat44 顶点变换 | 7.95% |
| 已解码 View::at 取值 | 5.73% |
| 视口变换 | 4.56% |
| 顶点缓存 get | 3.06% |

该线程 6,530 个样本中 **99.00% 位于原生 GL 库**，可确认当前主热点在几何后端。另一主要线程有 2,245 个样本，GL 占 9.35%，匿名可执行区域占 64.41%；本次没有记录 JIT 方法名，不能把匿名区域全部解释为游戏逻辑。

比例是 CPU 抽样归属，受内联影响，不是互相独立的墙钟耗时。尤其缓存写入可能归到内联的向量赋值，不能把上述比例直接相加预测 FPS。

## 选择顺序批次入口的原因

已展开的显示列表由 `java_prepared::View::at(i)` 设置 `sourceIndex=i`，同一批次的索引单调不重复，每次 draw 又初始化顶点变换器。因此这条路径仍然查询、写入 128 项变换缓存，却无法复用同批次结果。现有 `RIX_VERTEX_CACHE=0` 仅跳过查询，源码仍调用 put，不能完整去掉这段维护。

新候选为 GLX 实例使用独立命名的变换器及线程设备类型，保留旧方法，另外增加顺序入口：直接执行原 transform、图元装配和裁剪，跳过缓存 get/put，并直接初始化变换结果以减少临时搬运。原通用索引绘制继续使用旧方法；所有矩阵、向量、裁剪和三角形计算方法正文保持一致。

原 v4 核心头文件、类定义、静态库、DMA 驱动及 Renderer 不改动。已核对真实编译参数，核心库和 GLX 均为 `-O3 -DNDEBUG`，不是由 Debug 级别误编译造成低帧率。新类型只在 GLX 翻译单元实例化，按原编译参数重编译 GLX 后与逐项 SHA 固定的核心库链接，避免混用修改前后的同名 C++ 类型。不是对原类偷偷替换单个对象。

开关为 `RIX_JAVA_BATCH_CACHE_BYPASS=0/1`。两组都开启已验收的直接读取、整批提交、条带容量处理及析构后最终统计。新候选库 SHA-256 为 `8e89c36f66e497f26044c779551e5703fbbb7a1a02ff938c76315d8c99d4a993`，没有改变 JAR、纹理尺寸、几何数量、FPGA 逻辑或启用 FSR/CNN。

## 正确性与实机方法

主机对照旧变换器、新类型缓存开启和顺序绕过，96 次 draw、11,520 个输入顶点，覆盖三角形、四边形、线、点、裁剪与重复索引。11,710 个输出三角形的有效位置、颜色与两组 UV 共 **2,248,320 字节**，三者完全一致；不比较填充字节。R71 在切换 FPGA 前实际执行了 ARM 参考和新类型双模式，三者同样完全一致，ARM 原始字段 SHA-256 均为 `f7e4892117f3ad84d6eb1e9c951eec8eeed8e3a117dcf8ed8deadd1d68c78b40`。主机和 ARM 各自比较，不要求不同架构的摘要相同。

每轮继续验证原 42 幅原生回归图，并在同一二进制中增加缓存开／关的可见大批次探针：两模式各三幅、65,536 顶点、覆盖三个 GPU 条带、末尾标记、删除列表后消费及最终总量。两模式的整幅 RGBA 必须完全一致。

R71 的 ARM 字段及全部原生探针通过，但原版菜单的“Play Selected World”点击没有实际进入世界；辅助程序过早把一次鼠标发送视为完成，不再重试。240 秒后父运行器终止 Java，记录 exit=143、passed=false、restored=false、java_fps=null，硬件错误仍为零。按保守规则隔离当前启动周期，未删除或绕过保护。失败证据完整回读，单独保存；R72–R74 没有运行。

为此增加辅助程序的菜单重试：仍在选择页超过 3 秒，重新确认实际选中存档后重发鼠标点击。仅操作原版 GUI，不调用游戏内部加载方法。辅助程序正常关闭时限缩为 180 秒，与父进程 240 秒保护错开。随后回读并核对 13,380,568 字节 RAM 备份，正常 Linux 重启，保留历史隔离记录；通过旧控制器实际加载 v4、再恢复 v23，生成新启动周期的真实凭据后才继续试验。

新连续顺序为 **R75 原缓存、R76/R77 顺序绕过、R78 原缓存**。均采用同一候选二进制、同一冻结世界、和平难度、Tiny/Fast、60 秒暖机和约 30 秒配对计数窗口。新统计在渲染器销毁后输出，要求缓存路径及绕过路径的批次／顶点之和与最终队列消费完全相等。

## 实测结果

| 轮次 | 路径 | 完成帧／配对窗口 | FPS | Compiler 线程占一核 |
|---|---|---:|---:|---:|
| R75 | 原缓存 | 138 / 30.043054 s | 4.593408 | 8.31% |
| R76 | 顺序绕过 | 152 / 31.102590 s | 4.887053 | 32.72% |
| R77 | 顺序绕过 | 151 / 30.894182 s | 4.887652 | 13.79% |
| R78 | 原缓存 | 138 / 30.922716 s | 4.462739 | 8.72% |

原缓存两轮合计 276 帧／60.965770 秒，顺序绕过合计 303 帧／61.996772 秒；按完成帧和窗口时长加权 **4.527131 → 4.887351 FPS，+7.9569%**。两轮候选均高于两轮原缓存；这不是将不同库、不同启动周期的历史读数相乘。

剔除 Compiler 名称线程的采样平均占用 **1.06333 → 1.05143 核，仅下降 1.12%**；DMA FINISH 等待由区间的 **25.74% → 27.87%**。CPU 诊断窗口与 FPS 端点不同，不能据此声称每帧 CPU 或传输成本下降同样比例；等待占比升高也不能独立定位 GPU 内部算术瓶颈。

四轮均恢复 v23，硬件错误为零、所有冻结源文件和原选项字节不变。每轮 **48 幅原生 RGBA 回归图**，跨另外三轮比较 **55,296,000 字节**完全一致；每轮大批次的两种缓存模式也完全一致。R75 重新执行 ARM 三种几何检查，2,248,320 字节再次一致。实际游戏最终队列总量与缓存／绕过路径计数相等：

| 轮次 | 消费批次 | 消费顶点 | 实际使用路径 |
|---|---:|---:|---|
| R75 | 149,301 | 90,000,804 | 原缓存 |
| R76 | 164,192 | 102,658,992 | 顺序绕过 |
| R77 | 163,527 | 102,019,028 | 顺序绕过 |
| R78 | 226,937 | 90,150,720 | 原缓存 |

这些总量覆盖完整 Java 进程，含初始化、暖机、测量与退出，不能当作单独 30 秒内的几何数量。统计均在渲染器销毁和最后消费之后写出。

玩家位置、朝向与起始存档一致，Health=20、DeathTime=0。最终世界时间 R75 为 2239，其余为 2279；Compiler 负载也并不相等，候选 R76 尤其高。因此保留为本组观察收益，**不是独立因果加速比或长期稳定性验收**。世界截图会含移动动物、动画和时间差，不要求与回归探针一样逐像素相等。最大计数读取跨度 0.0945 ms。

## 后续优先级

### 对当前低帧率的判断

**PS 内置 Mali 没有接入本次游戏渲染。** ZU3EG 属于带 Arm Mali-400 MP2 的 EG 系列，Mali 自带一个几何处理器及两个像素处理器，硬件面向 OpenGL ES 1.1/2.0。见 [AMD GPU 架构说明](https://docs.amd.com/r/en-US/ug1449-multimedia/Graphics-Processing-Unit)。当前 Java 加载的是私有 RasterIX `libGL`，由 A53 处理几何前端、PL RasterIX 处理像素；`SOFTWARE_RENDERING=false` 只说明没有选择 CPU 像素光栅后端，不代表顶点变换也已硬件化。现有约4.89 FPS不能代表Mali硬件渲染性能。

可另做“Mali 完整3D渲染→PS DDR→PL后处理／显示”的对照，FPGA继续承担FSR和神经风格化。这属于渲染架构调整；原版Java/LWJGL的桌面OpenGL接口与现有Mali GLES驱动之间需要兼容适配，当前尚未验收。单独使用Mali几何、再交给RasterIX像素后端的拆分接口没有实现，不能仅切换一个开关。

最有证据支持的主因，是 **ARM 上串行的几何前端／三角形准备与命令提交链较重**。当前 CPU 执行显示列表处理、顶点变换、图元装配、裁剪、视口及三角形参数准备，FPGA 接着执行像素光栅、双纹理、深度和混合。`Rasterizer::rasterize` 在 CPU 侧计算包围盒、边函数初值与增量、颜色／纹理插值参数；并非只把原始顶点交给完整硬件几何流水线。几何工作队列仍由一个重工作线程处理，上传依赖和纹理／状态切换需要等待前序工作。

R76/R77 的最忙线程分别为 76.70%／75.68% 单核 CPU，另一主要线程为26.87%／26.60%，剔除 Compiler 后合计仍约1.05核。这与R70原生几何线程的函数采样共同支持“串行关键路径受限”，不能从四核总占用不高推断仍可直接获得数倍吞吐。

R76/R77命令流分别约33.50／33.17 MiB/s，按各自新帧率粗略折算约6.86／6.79 MiB命令数据／帧；该比值使用略有边界差异的诊断窗口，只作量级判断。实际纹理写入约7.43／7.49 MiB/s。DMA完成等待约占27.95%／27.78%，说明计算以外仍有明显等待；这些等待不能简单全部归入传输带宽或GPU执行。START ioctl累计仅约0.32%／0.31%，继续只减少发起系统调用已难以解释当前200多毫秒的整帧耗时。

因此，最近+7.96%解决的是一项真实开销，原来逐顶点／逐三角形的主要处理链仍在。下一项待证实的因素是：在DMA映射缓冲上细粒度生成命令是否放大CPU开销。普通RAM命令暂存目前只通过主机检查，没有缓存属性或实机收益的证据。FPGA的93% LUT是综合资源占用，不能用它作为运行时GPU满负荷的证明。

下一步应继续减少整批几何后端的临时搬运，研究保留原浮点运算次序的批量矩阵变换，并验证普通 RAM 命令暂存能否减少 DMA 映射上的细粒度写入。每次仍以原始字段、可见大批次和实际世界总量作约束。单个函数的样本比例不能直接当成可获得的 FPS 收益，也不能用只命中静止视角的缓存成绩代替移动场景。
