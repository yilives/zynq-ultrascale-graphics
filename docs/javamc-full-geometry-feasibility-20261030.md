# XCZU3EG 完整几何前端：容量与吞吐可行性复核

日期：2026-10-30。本文复核已有结果，不启动新综合、不修改渲染实现、不写开发板。

## 结论与此前判断的纠正

**当前 R45 不能与现有 RasterIX 底座一起装入 XCZU3EG。此前没有完成足以支撑“全功能前端可装入且达到目标帧率”的架构论证，就持续推进全量迁移，判断过早。**

此前完成的是余量检查、功能模型和若干面积实验。这些能够证明某些改动有效，不能证明最后一定能收敛到目标资源。后续不能再把“仍有优化设想”表述为“能够完成硬件接入”。

结论分三层：

1. 保持当前结构继续集成：**不通过**，缺口有实测依据。
2. 改成共享执行单元、字 RAM 和紧凑控制器：算术和存储容量**没有立即排除这个方向**，但完整控制、数学函数、端口和时序尚未获得资源证明。
3. 全功能前端装入后让 Java MC 稳定 60 FPS：**未证明**。当前输出接口还存在可计算的带宽上限，且缺少真实 MC 每帧工作量数据。

本报告不将第三项当作已具备可行性的工程承诺。

## 前端边界与25K数字的明确含义

这里的几何前端指顶点变换、图元装配、裁剪及三角形参数设置。**当前用于容量预算的无 FSR PL 底座不包含新增的这套几何前端。**现有可运行软件路径在 ARM 上执行几何处理，再向 PL 发送 RasterIX 命令与描述符；新 R45 是试图替换这部分 ARM 运算的独立硬件候选。

按底座已布线层级报告，LUT 分布为：

| 部分 | LUT |
|---|---:|
| RasterIX核心（不含新增几何前端） | 12,891 |
| 扫描、缩放及控制等GPU包装逻辑 | 5,060 |
| PL DDR4、DMA、互连及其余控制 | 20,099 |
| 无FSR底座合计 | 38,050 |

所以 38,050 不是一套“已经带几何前端”的 GPU 面积，也不能把 ARM 软件前端占用当成可释放的 PL LUT。R45 的 91,645 LUT 是额外硬件候选面积；现有 RasterIX 像素光栅化与新增三角形设置是不同步骤，不应重复实现已有后端。

**25K LUT 不是确定够部署的估算值。**下文的 25,454 是选定“整片预留10% LUT”后，反算出的新增几何 IP＋所有新增互连的预算约束。它不证明完整功能能被压入该预算；小原型达到这个数值也不自动证明完整功能、存储端口、带宽和整机时序合格。

部署至少需要完整目标功能的真实网表，在保留底座后通过全部资源检查、整机布局布线及时序、数据链路及设备验证。目前没有满足这些条件的25K完整几何前端。

## 1. 容量账：缺多少，而非只看有没有空闲 DSP

依据：无 FSR 底座的 `board/utilization.rpt` 为 Routed 状态；R45 为 Vivado 独立综合后的映射资源，非 HLS 面积估计。

| 资源 | 器件总量 | 无FSR底座 | 理论剩余 | R45几何IP | 简单相加 |
|---|---:|---:|---:|---:|---:|
| LUT | 70,560 | 38,050 | 32,510 | 91,645 | 129,695 |
| FF | 141,120 | 43,594 | 97,526 | 66,412 | 110,006 |
| DSP | 360 | 157 | 203 | 118 | 275 |
| BRAM36等效 | 216 | 71 | 145 | 41.5 | 112.5 |

独立综合和整机实现可能发生逻辑合并或增加，简单相加是工程容量预算，不是布局布线结果。但目前 LUT 缺口达到 **59,135**，没有证据支持靠普通集成优化消除这一缺口。

几何 IP 至少需要缩小到：

```
32,510 / 91,645 = 35.47% 的当前面积
必须减少 64.53% LUT，且还未给新增互连留量
```

若用“整片 LUT 不超过 90%”作为本项目的早期筛选目标：

```
几何IP＋新增互连预算 = 70,560 × 90% − 38,050 = 25,454 LUT
相对当前几何IP需减少 72.23%
```

90% 是这里明确选定的工程余量假设，不是 AMD 的强制标准，也不保证达到时序。DSP、FF、BRAM 的余量不能直接替代缺失的 LUT。

## 2. 为什么局部优化不能成为“能装入”的论证

R45 实际 LUT 分解为：

| 部分 | LUT |
|---|---:|
| 顶层自身控制、索引及数据访问等 | 34,137 |
| 裁剪、视口及三角形参数准备等 | 24,473 |
| 逐顶点变换、光照和纹理坐标生成等 | 20,857 |
| 独立法线矩阵控制 | 257 |
| 其他子模块合计 | 11,921 |
| 合计 | 91,645 |

这里的“顶层”是层级报告中的自身资源，不能把全部 34,137 LUT 都视为无用的状态机；它还承担图元、暂存、协议和数据访问相关逻辑。

对保持其余网表不变的局部修改，做两个特别乐观的减法：

- 把变换、裁剪/参数准备、法线矩阵三部分全部假设成零面积，仍有 **46,058 LUT**，超过 32,510。
- 把全部 7,558 LUTRAM 都假设免费，仍有 **84,087 LUT**。

因此只替换除法器、缩小一个矩阵函数、减少几个 DSP 或把部分 RAM 换成 BRAM，不能单独解决装入问题。即使把当前全部逻辑均匀减少 50%，仍需约 45,823 LUT。

这些减法只否定“保持当前其余结构”的局部修补思路，**不是所有可能几何架构的数学下界**。若重写控制和数据流，原有外围逻辑也会改变；收益必须重新测量。

## 3. 新架构为什么仍值得小规模验证，但不能保证成功

从本项目实际层级报告抽取同类浮点单元在现有上下文中的最大观测值：

| 单元 | 观测LUT | DSP |
|---|---:|---:|
| FP32乘法 | 93 | 3 |
| FP32加减 | 283 | 2 |
| FP32除法 | 789 | 0 |
| FP32平方根 | 445 | 0 |

例如，设想一个全局共享的“4乘＋4加减＋1除＋1平方根”算术组，仅按这些观测值相加：

```
LUT = 4×93 + 4×283 + 789 + 445 = 2,738
DSP = 4×3 + 4×2 = 20
```

**2,738 LUT 不是完整前端的面积估计，也不是新架构的综合上界。**这些单元原有上下文、端口和优化条件不同；此外还没有计入整数运算、比较与转换、pow/cos、寄存器文件、交叉选择、指令控制、裁剪与图元状态、AXI 接口等。

按前述 90% 整片目标，若这一算术组代理值可复用，其余所有功能合计必须控制在 **22,716 LUT** 内。这是需要证明的设计约束，不能把它当作已经做到的资源分配。

存储容量也可以列出一份条件预算：

| 规划存储 | BRAM36 |
|---|---:|
| 16,384×96 位控制ROM | 48 |
| 2,048×32 位工作RAM，两份复制 | 4 |
| 1,024×32 位状态RAM | 1 |
| 合计 | 53 |

这在 145 个剩余 BRAM36 内。块数按 1,024×36 的 TDP 配置计算，依据 [AMD UG573](https://docs.amd.com/r/en-US/ug573-ultrascale-memory-resources/Block-RAM-Summary)。但控制程序是否能装进 16K 指令尚未编译证明；两份 RAM 也只解决一部分读写端口需求，不能自动满足四乘四加的并行供数和写回。

所以目前最多能说：**共享执行架构在算术和存储的粗粒度容量上存在研究空间，完整 LUT 和性能仍未知。**不能据此承诺全量迁移可完成。

## 4. 运算吞吐：省面积会消耗周期

设目标时钟为 100 MHz，一帧 60 Hz 的预算是约 1,666,667 周期。以下只算当前公式的一部分工作，不是所有可能算法的运算下界：

- 一个原始顶点的稠密模型视图＋投影矩阵计算：32 次乘法、24 次加法。
- 双 TMU 启用时，12 个属性、各三个插值系数的点积：每个可见三角形 108 次乘法、72 次加法。

令每帧原始顶点数为 V，裁剪后的可见三角形数为 T。假设四个乘法器、四个加法器均能每拍启动一个操作，且没有数据依赖、供数冲突和控制停顿，则必要计算周期至少为：

```
C ≥ max((32V＋108T)/4, (24V＋72T)/4)
```

这还没包括 UV 矩阵、光照、裁剪、透视除法、包围盒与边函数、分区调整，以及 ARM 游戏逻辑和 RasterIX 光栅化。单元启动间隔与流水延迟不同；AMD [PG060](https://docs.amd.com/api/khub/documents/ym1A7qsltTGP_saZFTrikQ/content) 也明确区分每次操作的启动周期，不能把“有流水”直接等同于端到端每拍一个结果。

例如假设 V=10万、T=5万，计算下界已是 215万周期，即 **21.5 ms**。这个四乘四加设计点即使忽略其他成本，也达不到 60 FPS。扩大并行度会增加存储端口、选择网络和控制成本，必须同时算面积。

这里没有取得真实 MC 每帧 V、T、分区记录数 B、提交任务数 J 的完整数据，所以不能给出当前游戏的严格帧率预测。

## 5. 当前返回路径还有独立的带宽约束

生产 R45 RTL 明确为 `C_M_AXI_GMEM_DATA_WIDTH = 32`。在 100 MHz 设计点，理想连续写入上限为 400,000,000 字节/秒。

每条三角形分区记录写入：

```
2个记录头字＋49个GPU命令/描述符字 = 51×4 = 204字节
```

记录槽跨度虽然是 256 字节，但当前代码没有写满填充区；本计算用较乐观的 204 字节。模板记录、写响应和空拍等额外成本均未计入。

因此在 60 Hz 下，输出至多约 **32,680 条三角形分区记录/帧**。这是一条分区记录，不等于一个原始三角形。

| 假设每帧可见三角形 | 平均每三角形分区记录数 | 理想输出耗时 |
|---:|---:|---:|
| 20,000 | 1.2 | 12.24 ms |
| 20,000 | 2 | 20.40 ms |
| 50,000 | 1.2 | 30.60 ms |

这些是假设情景，不是当前 MC 的实测负载。第二行在计算和光栅化都不耗时的理想条件下，输出已把帧率限制到约 49 FPS；第三行约 32.7 FPS。

原始顶点至少还要读 80 字节/顶点，状态按任务读取，当前源代码有顶点有限性预检和后续使用两个遍历。ARM 还需检查并转发命令。以上均未加入这张最乐观的输出表。

所以仅压缩 LUT 不足以证明整条路线可用。若继续研究，还应考虑实际利用更宽的数据通路、减少分区重复描述符或采用有序直接流式衔接；这些都需要重新设计及验证，不是改一个位宽参数就完成。

## 6. 对后续路线的具体约束

**不再默认当前通用 C++ 前端经过局部调整就能收敛到容量目标。**原可运行 RasterIX 路线与 PL FSR 继续保留，不拿尚未可装入的完整前端替换它们。

下一次投入完整迁移前，至少先完成：

1. 统计代表性 MC 场景每帧 V/T/B/J、实际 OpenGL 功能和帧关键路径，区分平均帧与高负载帧。
2. 只做一个资源原型，包含真实接口、RAM 端口和最主要的控制路径。共享执行架构应先证明能满足约 25K LUT 的完整预算；不能用纯算术单元的面积替代它。
3. 用该原型的实际启动间隔、读写带宽和调度周期核对目标帧率。通过后再迁移其余通用功能；若只支持 MC 实际功能子集，需明确边界，不能继续称为全功能原前端。

**目前的决策是：现架构不适合集成；新架构可做受限验证，但完整可装入与 60 FPS 均未获证。此前的推进口径应据此收回。**
