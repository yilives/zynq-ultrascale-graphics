# RasterIX 游戏链路：风格化与渲染功能接入规格

日期：2026-10-18。本文保留实施前的建议设计，基线章节描述当时的源码和板测状态。后续已实现内容及验收结果见下方实施记录。旧 linestream-rs 方案作为研究资料使用，其中的任务、资源估算和原渲染器能力不直接视为本工程现状。

后续实施记录见 [POSTPROC_TOUCH_2026-10-18.md](POSTPROC_TOUCH_2026-10-18.md)。本文保留此前设计讨论的基线描述，新增模块的实际验收状态以实施记录和板测报告为准。

## 1. 实施前基线

当前链路：PS 游戏 / 顶点处理 → DMA → PL RasterIX IF 光栅与片元处理 → PS DDR RGB565 → rix_frame_bridge → PL DDR 400×240 XRGB8888 → axi_frame_reader → 24 位 RGB 解包 → scale2x_nearest → 800×480 LCD。

`src/rtl/top/rasterix_linux_top.v` 第 198–201 行是后处理接入点。当前仅最近邻 2× 放大，没有在游戏链路中运行 FSR、CNN 风格化或时域超分。旧工程有 FSR1 软件参考与风格化设计文档，不能据此声明对应 RTL 已接通。

当前 routed 报告 `report/board_utilization.rpt`、`report/board_timing.rpt`：

| 资源 | 已用 / 总量 | 数量上的剩余 |
|---|---:|---:|
| LUT | 25433 / 70560 | 45127 |
| FF | 33551 / 141120 | 107569 |
| BRAM 36 Kb tile | 77 / 216 | 139，约 625.5 KiB 原始容量 |
| DSP | 87 / 360 | 273 |

WNS +1.147 ns、WHS +0.010 ns，setup / hold 无失败端点。余量足以支持轻量流式后处理的初步设计；任何新增核仍需重新综合、布线、时序及上板验证，不能把资源数量剩余等同于可保证的时钟或吞吐。

## 2. 渲染功能应按位置实施

| 功能 | 当前情况 / 建议位置 | 实施边界 |
|---|---|---|
| 深度测试、混合、雾、纹理过滤 | RasterIX 已有相应固定功能，部分受当前配置限制 | 先核对游戏调用和硬件配置，避免重复实现 |
| 多个用户裁剪平面 | 当前 libGL / PS 顶点管线只暴露一个平面 | 优先扩展软件裁剪器；若搬入 PL，需新增几何输入、状态与调度，不能只改硬件开关 |
| 点精灵粒子 | 当前缺少点参数能力，部分装饰效果关闭 | 可先由 PS 将粒子展开为带纹理四边形；后续再评估 PL 展开器 |
| 模板阴影、镜面反射 | 当前 stencil 关闭 | 可以评估启用现有 stencil RTL；同时需要游戏对应几何、裁剪、模板状态和准确能力报告 |
| 第二 TMU | 当前一个 TMU | 可评估双纹理合并部分多遍绘制，但会增加纹理缓存、插值器、DSP / BRAM；性能收益需实测 |
| 256×256 纹理 | 当前最大 128×128 | 需同步修改缓存、页表、驱动与纹理池预算，再验证；后处理不会恢复原先未上传的纹理细节 |
| 任意 GLSL / 现代可编程管线 | 当前为固定功能架构 | 需要编译器、指令执行、寄存器和存储调度，是独立的大型 GPU 工程 |

软件接口缺失和后处理不是同一问题。新增描边模块不会自动补齐 OpenGL 调用；启用 stencil 也不会自动生成反射场景。

## 3. 首版：独立 RGB 风格化，不要求游戏改造

建议数据流：

```text
PL DDR 原始低分辨率颜色帧
  → AXI reader / RGB888 解包
  → 帧 / 行标记适配器
  → 颜色分级、色阶、可选 3×3 描边（400×240）
  → 2× 重采样（最近邻作旁路对照，再加入双线性）
  → 可选限幅锐化（800×480）
  → 输出缓存 / LCD 时序
```

建议新模块名：`rix_video_stream_adapter`、`rix_style_rgb`、`rix_upscale2x`、`rix_video_out`。这些名称为计划接口。

第一步仅做逐像素颜色分级 / 色阶，可定义原画、漫画色阶、复古调色三档。第二步增加 RGB 亮度边缘描边，再加入更好的重采样。RGB 边缘会把贴图纹理也识别成边缘，不能当成物体轮廓真值。

输入为 RGB888，采用 valid / ready，另加 SOF、EOL。现有解包流没有标准 AXI4-Stream Video 的帧 / 行标记，需由适配器根据已接受的像素计数生成。计数与窗口推进只发生在 valid && ready；背压期间保持数据和侧带稳定。若采用标准 Video 约定，TUSER[0] 为帧首、TLAST 为行末。frame_id 另通过帧描述符或明确的侧带扩展传递。

原 `scale2x_nearest` 只有两个源行 bank，并在输出使用后释放。增加 3×3 邻域时需保留相邻源行，设计额外行缓存及 bank 生命周期；边界采用复制或其他明确规则。预取实际从 VS 下降沿开始，在当前 525 行时序下距下次有效显示约有 29 行后肩时间；新算法仍需检查预填充、持续带宽及 presenter 源槽生命周期。

LCD 扫描不能接受任意停顿。输出侧必须有足够的行缓存，按固定像素时序读取；欠载按既有故障策略处理并计数。不能把 TVALID 直接当 LCD DE。算法延迟、HS / VS / DE、坐标、旁路延迟都需统一对齐。

首版采用小行缓存，不增加整帧中间颜色回写。处理发生在显示读流上，可能重复处理同一张被显示多次的游戏帧，适合轻量固定功能核。

## 4. Linux 控制与可回退

建议参数：style_mode、style_strength、color_levels、edge_threshold、edge_strength、upscale_mode、sharpness、可选 UI 保护区域，以及版本、处理帧数、输入 / 输出像素数、欠载和错误计数。

当前 PLGPU ioctl 尚无这些参数。需给新参数分配未使用的控制寄存器、更新 ABI / 配置标识、内核校验和 `plgpuctl`。旧 linestream-rs 文档中建议的 `0xA0000000` 在本工程已用于 AXI DMA，不能照搬。

参数采用 shadow / active 双份，在一帧边界整体提交，防止半帧切换风格。保留与原通路等延迟的 bypass。UI 首版可用固定区域 mask 保护，但各游戏布局不同；要准确保护 HUD 和菜单，需要游戏 / 驱动导出 UI 层或遮罩。

## 5. 第二版：深度感知描边

RasterIX 当前有深度测试，IF 自动装载 / 回写逻辑也支持 depth；PS 图形区为 depth 留有地址。这仍不等于已经有下游可稳定消费、与最终颜色严格配对的深度帧接口。

应先回读验证深度格式、行偏移和三个条带的完整性，然后在 GPU 释放该帧之前，将 Color / Depth 一起快照到下游缓冲，绑定相同 frame_id。当前单份 depth 会被下一帧复用；不能用上一帧的颜色配正在更新的深度。新增双缓冲或快照机制后，再实现深度断层描边、按距离调整线宽等效果。

深度可能是非线性窗口深度，阈值要在明确的深度空间定义。透明物体和禁用深度写的 UI 需要专门规则。normal、物体 ID 和逐像素运动向量当前没有通用游戏输出接口；旧自研渲染器的实验数据不能直接替代。

## 6. AI 风格化与超分的后续路线

若需要 AI 风格化，先选定固定风格的小模型，在 PC 用当前游戏回读帧验证效果与连续帧闪烁，再做 INT8 量化、逐层定点对照和硬件核。小网络是否能达到所需画风必须以样张判断，不能仅由通道数断言。

成本例子：三层普通 3×3 卷积，通道 3→8→8→3，需要 1008 MAC / 低分辨率像素。400×240×60 为 5.76 Mpx/s，共约 5.81 GMAC/s。假设新增计算核能收敛到 200 MHz、一个 DSP 每周期完成一个 MAC，理想下限也需约 30 个 DSP；实际还有利用率、量化缩放、加法、缓存及调度开销。旧文档的约 3 DSP 基于另一种约 100 MAC / 像素的假设，不是已实现 AI 核的测量结果。

CNN 采用流式特征行缓存或分块，避免把多通道整帧特征全部放 BRAM。较重或折叠计算的网络建议在计算域对每个新渲染帧处理一次，写入独立输出槽；处理完成后再提交 presenter。这样显示器可以继续扫描上一张完整图像。需增加缓冲所有权、完成握手、CDC 和带宽预算。

空间超分可按双线性 / 锐化 → EASU / RCAS 逐级增加。完整 FSR1 需要定点化、窗口、倒数等实现，不能把双线性加锐化称为完整 FSR1。已有软件参考可作为黄金模型。时域 ASR / NSS 需要进一步提供正确 MV、depth、jitter、历史和遮挡处理；当前游戏接入尚未具备这些输入。

800×480 显示目标约 60 Hz，对应 23.04 M 有效输出像素 / 秒，像素时钟还需覆盖消隐。固定功能后处理以活动区每周期一像素为目标。60 Hz 显示不代表把目前约 22–30 FPS 的游戏渲染提高到 60 FPS，也不包含插帧。

## 7. 实施顺序和验收

1. 用四款游戏回读帧做颜色分级 / 描边的软件样张，先决定画风、强度及 HUD 保护规则。
2. 接流接口与 bypass，逐像素比较 bypass 和当前输出；验证行末、帧首、边界、随机背压、复位和风格切换。
3. 落颜色分级 / 色阶，再加描边行缓存、双线性 2× 和限幅锐化。每次新增后重新综合布线，检查资源、时序与 CDC。
4. 四款游戏逐个测试原画 / 风格切换，确认无撕裂、欠载和 DMA 错误，并分别测唯一呈现帧率、显示刷新率与新增延迟。
5. 完成与颜色配对的深度快照，再做深度描边；AI 模型和时域超分分阶段验证。

首个明确交付目标是：四款游戏共用原画 / 漫画 / 复古风切换，支持可回退的放大与锐化，继续保留已验证原画通路。该目标不依赖通用可编程 GPU 或运动向量。
