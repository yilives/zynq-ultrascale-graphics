# AXU3EG 游戏运行时第二轮优化（2026-10-19）

本轮交付降低 Linux 监测和日志开销，并用实板计数定位下一处渲染瓶颈。游戏、原生模块、libGL、SDL 共 12 个二进制文件与上一轮逐字节一致，现有画质和 FPGA 工程参数保留。

## 直接读取硬件状态

原启动器每 0.5 秒启动一次 `plgpuctl`，随后解析 JSON。现在通过持久文件描述符直接调用 `PLGPU_GET_STATUS`，按驱动头文件的 64 字节、16 个 u32 解码；文件描述符设置 close-on-exec，退出时关闭。ABI 或配置摘要不匹配时拒绝继续，硬件故障位会保留到结果记录。

实板空闲状态各读取 100 次，全部 16 个字段与原 C 工具一致：

| 状态读取方法 | 单次墙钟耗时 | 单次 CPU 时间（含子进程） |
|---|---:|---:|
| 原外部进程 | 4.263 ms | 4.722 ms |
| 直接 ioctl | 0.0455 ms | 0.0454 ms |

该项采样约快 94 倍。这个数字衡量监测调用，不代表游戏渲染速度。

## 有界日志与完整错误检测

新增独立线程持续读取游戏 stdout/stderr。已有的 `glHint not implemented`、`glDrawBuffer not implemented` 两种完全匹配的重复提示保留首次记录，之后计数；它们的 OpenGL 行为没有改变。

主日志最多 8 MiB，独特输出超过该大小时继续读取并保留最后 64 KiB 到 `game-tail.log`。所有原始字节仍参与 DMA 错误和裁剪警告计数，日志大小不再触发游戏提前结束。真实读取/写入失败仍会结束本次运行并记录原因。

`result.json` 新增 `diagnostic_stream`，记录输入量、保存量、重复次数、溢出量、尾部大小、完整流错误计数和读取失败；`telemetry_backend` 标记实际状态读取方式。

主机和 A53 均通过真实 PIPE 压力测试：18,750,026 字节的输入保存为 101 字节，250,000 次重复提示有完整计数，末尾 DMA 错误仍被检测到。另一个测试在日志超限后及 64 KiB 分块边界注入错误，验证计数和尾部数据。A53 的极短行压力测试暴露了原 5 秒排空时限不足，已修复为有界的 30 秒等待。最终五项测试（含 boot ID 故障隔离）全部通过。

## 五游戏回归

| 游戏 | 上轮实际 FPS | 本轮实际 FPS | 本轮日志减少 |
|---|---:|---:|---:|
| Neverball | 28.50 | 28.14 | 无重复提示 |
| Neverputt | 30.00 | 30.03 | 无重复提示 |
| Quake I | 30.04 | 30.07 | 88.3% |
| Quake III | 28.51 | 28.45 | 84.8% |
| Tux Racer | 30.05 | 29.99 | 98.0% |

这些小幅帧率变化在固定场景的重复测量波动范围内，本轮没有宣称渲染提速。Tux 五分钟原始输出 2,268,991 字节，保存 45,241 字节；29,650 条重复提示改为计数。

本轮继续使用上一轮的固定场景、全新配置和 12～39 秒比较窗口，实际 FPS 取硬件 `presented` 增量。Tux Racer 延长至五分钟，包含自动开局和比赛结束；这项测试不等同于半小时或多小时热稳定性验收。

软件交付的 **106 项检查通过**，包括固定场景、五分钟 Tux、完整流压力、最终五游戏入口、模拟故障拦截，以及正常重启后的模块/配置摘要和 9,246 个 GPU 像素检查。下述实际切换超时作为已知问题保留，因此没有宣称连续切换或长时稳定性问题已全部解决。

连续切换曾在 Quake 加载时发生一次 DMA `errno=110`，此时显示错误计数仍为零。失败原始记录保留在 `report/postproc_games_opt2_observed_failure.bin`；相同配置经完整重启后独立通过，随后整套五游戏序列再次通过。根因尚未定位，未把这次失败归类为已消除的问题。

最终启动器在 DMA/显示错误或进程异常退出后写入包含 boot ID 的恢复标记，同次启动中的后续 `rix-games` 调用会被拦截，要求正常重启开发板。实板用明确标注的模拟标记验证了公开入口的拒绝行为：GPU 计数完全不变、没有创建游戏目录，测试后恢复原标记。该测试没有注入真实硬件故障。恢复标记与详细失败结果一起保存，避免只看显示状态正常就继续复用异常链路。

## 帧链路的实测瓶颈

使用新 ioctl 读取工具，观测 SWAP、COPY_DONE、实际 LCD 呈现三个计数变化，在 FPS 比较窗口之后采样。

每次观测 12 秒、360 个完整帧，无漏计数转换：

| 阶段 | 500 µs 请求间隔（比赛中） | 2 ms 请求间隔（结束画面） |
|---|---:|---:|
| 接受 SWAP → COPY_DONE | 18.36 ms | 17.32 ms |
| COPY_DONE → 实际呈现 ACK | 9.85 ms | 10.81 ms |
| 前帧 ACK → 下一次 SWAP | 5.24 ms | 4.34 ms |

实际采样间隔中位数分别为 0.653 ms 和 2.160 ms。复制耗时的观测区间中位数分别为 17.66～19.07 ms、15.10～19.54 ms。两次观测的游戏状态及采样分辨率不同，结果差异不能全部归因于采样开销。

区间上下界来自相邻采样时刻，表示观测分辨率，不是统计置信区间。前一帧呈现到下一次 SWAP 的间隔包含 CPU、命令上传及 GPU 处理，未单独命名为光栅化时间。

当前 `src/rtl/gpu/rix_frame_bridge.v` 使用单拍 AXI 读取、单拍扩展写入，每组四个 RGB565 像素等待读响应和写响应后才处理下一组。400×240 每帧需要 24,000 次读事务及 24,000 次写事务。实测指向这段串行搬运的延迟：60 FPS 的总预算为 16.67 ms，而本次复制阶段的典型耗时已超过它。

后续 FPGA 优化应集中于突发读写和缓冲流水，同时保留 4 KiB 边界、AW/W 独立握手、B/R 响应排空、快照租约、逐像素格式转换与 vblank 换帧保证。本轮软件交付使用既有 bitstream；尚未把突发桥接设计作为已上板功能。

## 交付与使用

公开入口保持：

```sh
rix-games neverball --seconds 1800 --filter bilinear --style original
rix-games neverputt --style poster
rix-games quake --style sepia
rix-games quake3
rix-games tuxracer
```

配置位于 `/opt/rasterix/experimental/profiles/<游戏>/`，逐次结果位于 `/opt/rasterix/experimental/results-optimization-20261019/`。安装收据包含新支持模块及实际系统 Tux Racer 摘要；仅更新脚本时也会如实保留“原生 Tux 与当前包匹配”的状态。

当前包 `game-runtime.tar.gz` 为 3,980,412 字节，SHA-256：`6d35f2b7bafbf054b1a32c44cd4a3c9d71add5010bb91702db3be60d1f428269`。两次打包摘要一致，JTAG 传输经过逐块和整包校验。上一轮运行包、清单和脚本保存在 `report/game-optimization-20261019/round2/previous-release/`；板上旧脚本保存在安装收据指向的备份目录。

五分钟及 FPS 测量包保存在 `round2/measured-release/`。最终包追加故障隔离；直接状态读取类和日志类的 AST 与测量版一致，12 个二进制文件摘要也一致。最终包另行完成五游戏安装入口、故障拦截和重启验证。

更新时安全空间检查曾拒绝接收新包；三个已淘汰候选包共 11,936,607 字节已经完整校验复制到 FAT 分区后才移除原副本。当前包、上一版回退包和启动文件保留。接收器已改为先检查剩余空间，再移走旧缓存；传输工具会自动上传维护在 `linux/game_port_receive.py` 的接收端。

机器可读结果见 [第二轮验收](../report/game-optimization-20261019/round2/acceptance.json)，上一轮缓存、裁剪和纹理优化的历史结果见 [五游戏优化记录](GAME_OPTIMIZATION_2026-10-19.md)。本轮未重新生成整卡 `.img`。
