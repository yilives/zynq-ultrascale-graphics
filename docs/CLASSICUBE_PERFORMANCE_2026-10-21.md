# ClassiCube 异步流水与实际 LCD 帧率

本轮保持键鼠版完整 400×240 渲染、800×480 最近邻输出、64³ 真实地形和 32 格视距，优化提交调度和软件限帧。游戏渲染与输入适配、纹理、RasterIX 库和 FPGA 配置沿用键鼠 v9；启动器默认采用异步流水和 120 FPS 的 CPU 提交上限，原生诊断模块补齐异步读帧同步。实际 LCD 刷新仍约 60 Hz。

当前交付版复杂路线长测为 **57.31 FPS**，原调度为 **42.19 FPS**，提升 **35.8%**；轻负载约 60 FPS。以下历史对照用于说明调度、限帧与取证方法的选择。

## 改动及依据

原默认 `pipeline` 每次交换前等待顶点工作线程、DMA 上传线程和上一帧显示完成。ClassiCube 已把当前帧顶点复制进命令列表，后台又有独立列表双缓冲和复用前的等待；这个额外的全队列排空使原本可以重叠的计算与传输串行。

新默认选择现有库的 `async` 路径，保留后台列表双缓冲、DMA 完成等待、FPGA 帧交换应答以及退出时的完整排空与呈现检查。启动器强制 `RIX_PRESENT_SYNC=1`，不会因旧 shell 的同名环境设置而关闭最终检查。

同步关系可在本地源代码核对：

- `ThreadedVertexTransformer::streamDisplayList()` 在复用源列表前等待工作线程。
- `swapAndUploadDisplayLists()` 在交换目标列表前等待上传线程与 DMA。
- `DeviceDataUploader` 在发起下一笔传输前等待当前 DMA。
- `rix_frame_bridge.v` 在 LCD 确认呈现后才应答帧交换。
- GLX 销毁上下文前等待两个后台队列、DMA 和最终硬件呈现。

没有减少视距、缩小客户区、改低纹理精度或增加 FPGA 资源。短测日志中 CPU 绘制平均约 5.75 / 5.81 ms，交换调用的平均阻塞从约 11.66 ms 降到约 0.02 ms；异步模式的工作转移到后台，因此交换耗时不能解释成 GPU 完成耗时。

## 性能与验收

完整结果由 `report/classicube/performance-acceptance.json` 和 `performance/long-matrix.json` 记录，数值来自硬件 `presented` 计数。每轮预热两秒，自动路线按时间驱动，而不是按软件帧数推进。

第一阶段隔离调度因素，软件上限统一为 60 FPS：短测顺序为原流水、串行、异步、原流水，每次运行 18 秒、有效测量约 16 秒；长测采用原流水、异步、异步、原流水的交叉顺序，每次运行 62 秒、有效测量约 60 秒。所有对照使用同一游戏二进制、库、地图种子和 32 格视距。

| 有效测量窗口 | 原流水 | 异步流水 | 提升 |
| --- | --- | --- | --- |
| 约 16 秒短测 | 48.00 FPS | 56.58 FPS | 17.9% |
| 两轮各约 60 秒长测的合并结果 | 42.06 FPS | 55.13 FPS | 31.1% |

长测原流水两轮分别为 41.88、42.24 FPS；异步两轮为 54.65、55.61 FPS。完全串行的短测为 39.15 FPS，未采用。

第二阶段检查轻负载回退：60 FPS CPU 上限下，平地异步呈现只有 57.61 FPS，原流水为 60.05 FPS；异步的 CPU 上限改为 120 后，平地与真实地形短测分别达到 60.23、60.24 FPS。平地三种配置的完整 GPU 原图 SHA256 完全一致，未改变画面质量。最终配置按“原流水 / CPU 60”与“异步 / CPU 120”再做四轮交叉长测，结果单独记录，避免把软件提交帧率当作 LCD 帧率。

最终交叉长测：原调度两轮 42.16、42.13 FPS，合并 42.15 FPS；新默认两轮 57.43、57.57 FPS，合并 57.50 FPS，提升 **36.4%**。短测和轻负载约 60.2 FPS；复杂路线仍会降帧，不能表述为全程锁定 60 FPS。

该交叉长测的第二张异步截图曾发现 GPU 原图与 LCD 有 1,004 / 6,000 个采样点不同。失败的原始归档和 `pixels.json` 保留，未记为图像验收通过。读取 GPU 内存不等于 LCD 已完成换帧，因此诊断启动器和独立输入测试都增加了硬件呈现检查：冻结提交后，等待 `frame_id / swap / copy / presented / last_presented` 一致且稳定，再采样 LCD，并确认采样期间帧号不变。这个等待只用于截图，不加入正常游戏的每帧路径。

修复还覆盖“帧号不变、待显示状态转为已显示”的等待分支，主机回归直接执行真实等待函数。第一次截图修复版另做两次 62 秒长测，实际 57.34、57.58 FPS，合并 57.46 FPS，相对原调度提升 36.3%；同时核验八个连续转向视角与完整键鼠流程的 GPU / LCD 对照。

随后存档重载又捕获到 24 个文字像素不同，说明读取 GPU 原图本身也必须等待完成。该失败归档同样保留。最终原生截图采用两阶段读取：第一次读取只用于排空 CPU 队列与 DMA，随后等待 GPU / LCD 的帧号一致稳定，再进行第二次原图读取。FPS 的结束硬件计数在整个截图流程之前封存；早期截图后取数的历史结果可能包含少量排队帧，当前性能结论以同一修复版二进制的交叉长测为准。

最终原生修复版重新进行四轮交叉长测，同一二进制、严格的截图前计数窗口：原流水 42.29 / 42.09 FPS，合并 **42.19 FPS**；异步 / CPU 120 为 57.29 / 57.38 FPS，合并 **57.34 FPS**，提升 **35.9%**。前述早期数据保留用于分析，当前交付性能采用这组结果。

继续取证确认：异步模式下，OpenGL 假定的 front 读回可以领先于硬件实际送显的帧。10 秒文字消退边界处，OpenGL 原图与实际送显源有 271 个完整像素不同；硬件记录的 PS 槽为 `0x60200000`，该槽的完整 RGB565 图像却与独立 LCD 采样零差异。原 OpenGL 原图和失败记录全部保留，不能把它们描述为 OpenGL 读回已修复。

交付版因此同时记录两类数据：`native.ppm` 作为 OpenGL 读回诊断，`presented.bin/json` 作为硬件实际送显源及帧号证据。只有在原生诊断明确冻结、CPU/DMA 队列排空、硬件呈现完成且游戏锁仍持有时，才读取硬件 `last_source` 指定的 PS 槽；读取两次的数据、GPU 命令/忙计数、帧号和源地址必须保持一致，再与 LCD 输出样本比较。该方法不用于运行中的实时取帧；实时超分和 CNN 仍使用原 SNP1 租约。

最终取证包在相同原生二进制上复验两轮长测，合并 **57.31 FPS**，相对 42.19 FPS 基线提升 **35.8%**。以下最终验收按硬件实际送显源进行，OpenGL 假定 front 的差异独立披露。

最终整体验收 **41/41**。交付包的两次长测、重载、正常重启、五个界面和八个转向视角，共 17 组参考、**102,000 个 LCD 采样点零差异**；连同本轮基线及中间控制的有效参考，总计 216,000 点，失败截图另存。键鼠主机核验为 20/20。菜单存档经独立 NBT 解析，全部 65,536 个方块在重载和正常重启后保持一致。

正常重启后的启动 ID 为 `c7360927-9627-4e1e-8231-5a2ae39748ea`，程序和共享运行时均从空 RAM 缓存恢复，客户区仍为 400×240，焦点与相对鼠标模式正常。收尾 GPU 呈现计数 483，错误、隔离标记、快照占用和超时均为零；原 BOOT、DTB、共享 GL 和 31 个 CNN 安装文件保持相同摘要。

自动输入仍走 `XTEST → X11 → SDL2 → 游戏输入处理器`，不以内部 autoplay 代替键鼠测试。验收还覆盖菜单指针、存档、重载、早退、旧 GLX 入口及正常重启后的持久启动。GPU 原图与真实 LCD 采样逐点比较；菜单保存的地图由主机独立解析全部方块，再与重载结果比较。

这些测试不包含实体键鼠手感、DPI 或输入到光子的延迟测量。异步流水可能增加排队延迟；若需要比较操作延迟或排查问题，可临时使用原调度。真实游戏帧率仍随地图、视角和视距变化，60 FPS 上限不代表复杂场景始终达到 60 FPS。

## 使用和复现

```sh
rix-classicube
rix-classicube --present-strategy pipeline --fps-limit 60
rix-classicube --present-strategy serial --fps-limit 60 --seconds 18 --autoplay --capture
```

默认持续运行，正常从菜单退出。`--present-strategy` 的选择会写入本次 `result.json`，只影响该次启动。键鼠和菜单操作见 [键鼠版说明](CLASSICUBE_KEYBOARD_2026-10-21.md)。

主机构建仍为 `build.ps1 -Action classicube`。板上对照脚本为 `linux/classicube/performance_qa.py`，输入与重启回归为同目录 `performance_followups.py` 和 `performance_coldboot.py`；主机使用 `verify_classicube.py`、`verify_classicube_input.py` 与 `record_classicube_performance.py` 核验。

原 v9 包和启动器已保留在 `build/classicube/performance-v9-baseline/`，中间候选保留在 `build/classicube/performance-v10-candidate/` 至 `performance-v14-candidate/`；板上旧包按 SHA256 存入原 ClassiCube SD 归档。本轮将三个有摘要命名的旧启动器压缩归档并逐文件回读后释放根分区副本。部分旧候选在确认主机已有完整、同摘要备份后从 SD 迁回主机，SD 保留原收据和 `.host.json` 定位信息；当前 v9 和其余候选仍保存在 SD。32 MiB 根分区和 16 MiB SD 空间保护阈值保持不变。
