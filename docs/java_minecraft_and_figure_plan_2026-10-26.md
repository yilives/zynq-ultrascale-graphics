# 官方Java版Minecraft可行性与参赛对比图安排

日期：2026-10-26。本记录回应“官方Java版能否跑得动”，并整理现有图像如何支持参赛文档。选型分析写于实测之前，后续结果见下方更新。

后续已按用户要求实际尝试官方1.2.5：ARM64 Java、AWT、LWJGL和GLX上下文通过，客户端在256×256启动图片上传处触发128纹理上限错误，尚未进入菜单或世界。详见[独立板端尝试记录](minecraft_java125_board_attempt_2026-10-26.md)。下面保留选型分析和对比图安排；有效游戏帧率仍未取得。

## 1. 直接判断

**早期官方Java版有尝试空间；现代Java版不能直接接入当前RasterIX渲染路径。现在还不能给官方Java版承诺FPS。**

Java语言或ARM64本身不是绝对障碍。[Minecraft当前官方产品页](https://www.minecraft.net/en-us/store/minecraft-java-bedrock-edition-pc)列有ARM64架构，[LWJGL当前官方构建](https://www.lwjgl.org/browse/stable/bin/lwjgl-glfw)也有Linux ARM64原生库。但现代LWJGL包并不能直接替换旧客户端所需的LWJGL版本，JVM能启动也不等于原版图形接口已兼容。

| 官方Java版本方向 | 当前项目判断 | 两周内的取舍 |
|---|---|---|
| 现代版本，以1.17及之后的现代渲染架构为代表 | 与现有固定功能实现存在根本图形接口缺口 | 不作为本次两周迁移主线 |
| 1.7.10、1.12.2等较老正式版本 | 需逐项核对客户端、LWJGL/native、纹理、扩展和渲染调用；不能只因“老版”就认为可直接运行 | 没有兼容实测前不承诺可玩或帧率 |
| 更早的Beta/早期正式版本，例如Beta1.7.3或1.2.5 | 可作为小型兼容验证的候选；此处是工程选型建议，尚未核验这些版本的全部调用 | 只挑一个，设置1–2天的兼容验证关口，失败则不影响现有参赛版 |

官方[1.17发行说明](https://feedback.minecraft.net/hc/en-us/articles/4402626897165-Minecraft-Caves-Cliffs-Part-1-1-17-Java)明确该版本转为OpenGL 3.2 core、以着色器替换固定功能渲染。2026年官方又公布向Vulkan迁移，并保留过渡期选择/回退；具体状态随版本变化，不应把所有版本概括为始终只用同一API。无论哪条现代路径，都不是当前RasterIX固定功能接口的直接替换对象。

## 2. 已经核实的项目限制

当前链路为：官方客户端若要接入，需经过ARM64 JVM、该客户端对应的LWJGL/JNI、兼容GL/GLX库，最后才能进入PL RasterIX。FSR和CNN是后处理，不会补齐前端缺失的图形接口。

源码核查：

- [glNewList.cpp](../external/tuxracer/RasterIX/lib/gl/opengl/glNewList.cpp)只有未实现警告。
- [glCallList.cpp](../external/tuxracer/RasterIX/lib/gl/opengl/glCallList.cpp)中的单个/多个列表调用同样只有未实现警告。
- [glGetString.cpp](../external/tuxracer/RasterIX/lib/gl/opengl/glGetString.cpp)报告固定功能接口版本；未提供现代完整着色器管线。
- [实际项目配置](../config/rasterix_axu3eg.json)将最大纹理设为128。早期客户端的纹理图集、尺寸与分页行为需要单独核对，不能照搬ClassiCube的分页适配结果。

前三个源文件SHA已与v26构建所用原始534文件清单核对一致，不是仅检查了一个与当前构建无关的上游副本。ClassiCube使用经过适配的GL1 VBO路径并避开不支持的显示列表；其正常运行不能证明官方Java客户端已兼容。

因此有两类成本：先把窗口、图形API、纹理和世界画面接通，再处理Java侧世界生成、对象分配/GC、实体/物理、网格及提交成本。ClassiCube约57 FPS不构成官方Java版也能达到相同帧率的证据。

## 3. 如果要验证，怎样最快得到有用结论

1. 固定一个早期版本，通过用户拥有的合法客户端/官方渠道取得所需文件，不把游戏本体混入开源参赛源码包。
2. 先核对ARM64 JVM、对应LWJGL及其native库、X11/GLX和库加载路径，跑出真实的Java图形探针。
3. 验证该版本实际需要的GL调用；专门覆盖显示列表、纹理尺寸/上传、深度、混合与输入。不能以伪造版本字符串绕过能力检查。
4. 必须进入有地形的世界，正常移动和退出；不能以启动器或主菜单出现就宣称“原版跑通”。
5. 固定400×240、小范围场景，分别记录世界生成耗时、稳定游玩源帧/最终输出、p99、内存及错误，再决定是否值得继续。没有实测前不给10/20/30/60 FPS估计。

若关键兼容项需要大改，维持现有ClassiCube参赛主线，官方Java作为后续工作。若改用PS GPU、CPU软件渲染或PC串流，应明确新链路；这些结果不能证明官方客户端在RasterIX上完成渲染。

## 4. 对比图：应该多，但每张必须支持一个判断

当前扫描得到：`report/classicube`有322张PNG，CNN质量v5目录50张、FSR实现各版本91张、10月23日插值/FSR比较目录16张。这些包含重复视角、历史版本、参考图和诊断图，不是479组独立有效实验，也不代表最终报告已经排好版。

建议正文组织12–16张关键图，更多原始图进入附录。正文图按“问题→候选→证据→选择”组织，而不是堆截图。

| 建议图 | 要回答的问题 | 当前素材与状态 |
|---|---|---|
| 1. ARM/PL及帧数据流图 | 哪些工作在ARM，哪些是FPGA硬件？ | 可从已有架构和源码绘制，注明顶点前端仍在ARM |
| 2. 独立启动与实体交互 | 作品是否能不依赖开发电脑正常演示？ | 需要最终发行版冷启动照片/录像及实体键鼠补验，旧串口日志不能替代 |
| 3. 最近邻/双线性/FSR同源全图 | 三种算法改变了什么？ | 已有三组同源输入图；是CPU算法参考对比，不能标成最新v23的三组FPGA截图 |
| 4. 同坐标局部放大 | 斜边、纹理、物品栏有哪些收益或损失？ | 已有crops，须统一裁剪/倍率，说明锐化与像素形状变化 |
| 5. 浮点参考/定点实现/实际FPGA差异 | 硬件实现是否符合定义？误差在哪里？ | 最新v23有归档数值证据；最终稿应从匹配该版本的原始数据导出图，不复用旧版本PNG冒充 |
| 6. 同帧原图/旧模型/新CNN | 模型修改产生什么变化？ | v5已有；旧模型列是离线整数参考，新模型列经FPGA/LCD检查 |
| 7. 教师模仿与结构保留 | 更接近教师是否也更适合MC？ | 有留出对比和MAE；不能把MAE下降当成人工审美评分 |
| 8. 隐藏通道活动 | 为什么要修复零通道？ | 已有channel-activity.json，适合绘6/8→8/8通道热图 |
| 9. 真实运动序列 | 风格化有没有闪烁/拖影？ | 目前500 ms采样代理有记录；最终需连续运动视频/序列，不能只挑静帧 |
| 10. CNN核心与完整链路成本 | 为何不继续盲目增加卷积并行度？ | 核心周期、PIO和端到端报告已有；重叠阶段画时间线或分别列出，不全部相加 |
| 11. FSR缓存/调度前后 | 真正收益来自哪里？ | 有多版本板测；示意图与实际计时分开，跨场景数字不拼成严格加速比 |
| 12. v26平均FPS与帧间隔 | 为什么平均更高仍不替换默认？ | 现成ABBA原始验收可绘FPS、p99/CDF和长间隔对照 |
| 13. v25/v27失败候选 | 哪些看似合理的选择实际无收益？ | LTO/亲和性对照已有；各自实验独立作图，保留失败结论 |
| 14. 最终整机资源与时序 | 新功能的资源代价是否值得？ | 整机报告已有，勿将OOC数字混入整机对照 |
| 15. 组合链路同帧与性能 | 风格+FSR是否真的已实时接通？ | 尚待实现与取证，现在只能画明确标注“拟议”的架构图 |
| 16. 复现/退出/恢复 | 别人能否重建并可靠重复使用？ | 有旧验证材料；需最终发行版本的闭环补证 |

每张图注应含版本/模型、输入或场景、分辨率/视距、执行位置、参考还是实测、主要结论与限制。性能图应能追到原始JSON、窗口与SHA。
