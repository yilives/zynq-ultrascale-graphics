2026-10-27。**四轮交叉短测，原版 Java 世界新帧率由加权 6.879 提升到 7.480 FPS，约 +8.73%。** 本轮使用已实测的双 TMU 位流。源渲染 400×240、完整 256×256 纹理、Tiny/Fast、关闭云，最近邻呈现；没有加入 FSR 或 CNN。全部为 RAM 试验，目前仍不流畅。

## 先测量，区分事务开销和传输总量

私有诊断库只在设置 `RIX_JAVA_DMA_PROFILE` 时记录传输分类、字节数和 START/FINISH ioctl 时间。父进程另以 0.5 秒周期读取 `/proc/<Java PID>/task/*/stat`，按 Java 的单调时钟标记截取活动世界区间。原版客户端 JAR SHA-1 仍为 `4a2fac7504182a97dcbcd7560c6392d7c8139928`。

R25 有效基线：21.003 秒内完成 144 个实际显示新帧，**6.856 FPS**。其中 20.391 秒统计子区间有 **233,202 次纹理 STORE**，约 457.3 MiB；2 KiB 小写事务占主导。START ioctl 累计约 7.25% 区间时长，FINISH 等待约 33.96%。两个最忙的游戏/驱动线程分别约占一核的 75.8% 和 59.1%；JIT 编译线程也仍在运行。这些量彼此可能重叠，不能相加当作完整帧时间分解。

入口总数据也包含几何/状态/协议，不能全部称为纹理或全部归因于填充。`perfBusy` 仍是 CommandParser 非空闲标志，不能当作整块 GPU 利用率。

## 实际改动

在 `ThreadedVertexTransformer::textureUpload()` 内，将**地址严格连续、保持原顺序**的 2 KiB 暂存页合并为最多 **64 KiB（32 页）**的写入。地址出现间隔、逆序、重复，或合并后超过上限时，先提交当前批次。使用 64 位地址计算检查连续性，避免跨越 32 位地址边界误合并。

纹理页字节不变，页分配和纹理绑定不变；没有通过缩小纹理、减少视距、关闭第二 TMU 或跳过绘制提高帧率。写入失败继续抛错，未全部提交前不清空暂存列表。批次数据由底层同步复制到专用 DMA 缓冲后提交，后续复用临时 CPU 数组不改变已提交数据。

硬件没有重建，资源仍为 LUT 65,624/70,560、BRAM 149/216、DSP 330/360。匹配候选库 SHA-256：`2abdf91548cc56476eb7803d7d69d694818f103e3586e2a6940a39011524d38c`。538 项编译输入通过指纹核验，软件像素渲染关闭。

八组宿主检查逐字节核对连续页、容量截断、间隔、逆序、重复地址、地址边界、空队列及失败传播。板端继续检查真实双纹理、九组显示列表、完整纹理/Mojang、5 MiB 上传、glFinish 及换页；每轮实际世界结束后恢复 v23 和原始配置。

## 世界起点及拒绝的 R24

每次从冻结存档复制新的私有世界，通过原版菜单选中它，核对 GUI 实际选中项的文件夹名后才点击 Play Selected World。固定位置与视角，预热 10 秒，采样约 20 秒，然后正常退出。旧试验世界保存在对应结果目录，避免世界列表不断增长。

R24 最初只计算了列表行坐标，未考虑短列表垂直居中，实际误选 R23。原存档哈希变化使整轮明确判为失败，**不参与性能比较**。未使用的 R24 副本与 R24 前的全部文件哈希一致；在空闲锁下保留误选后的存档，再逐文件核对恢复 R23，并在世界列表外建立冻结基线。恢复记录为板端 `java256-world-r24/save-repair.json`，误选后存档另行保存。R25 起增加实际选中项核对，原始基线哈希在每轮结束后验证。

活动采样边界允许一帧正在复制/呈现，因此 FPS 只使用 `presented` 的增量。最后退出时仍要求队列完全排空，不能将提交帧或 LCD 重复扫描次数计入游戏 FPS。

## 下一步应减少真正传输的数据

合并只减少小事务的 ioctl 与调度成本，不消除纹理数据本身。源码核对发现，现有 `TextureMemoryManager::updateTexture()` 会重新分配整纹理页并全部标脏；局部纹理更新可能因此产生整纹理上传。下一轮应先核对动态纹理的实际更新频率与不变页比例，再评估按物理页内容跳过完全相同的写入，或引入正确的局部更新与页生命期管理。

不能直接按脏矩形覆盖旧 GPU 页：显示列表与上一帧可能仍引用这些页，必须保持更新顺序、缓存失效和 GPU 在途引用的正确性。后续还应采样顶点处理、显示列表重放与 Java/JIT；本轮尚未证明某个单一环节解释全部低帧率。
