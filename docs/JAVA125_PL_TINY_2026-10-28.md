# 原版 Java：正确 Tiny 视距的 PL 复测与 Mali 对照

2026-10-28。用户要求解释 Mali 表现并实测 PL 的 Tiny 视距。本轮保留原版 Java 1.2.5、400×240、完整256×256纹理与双TMU，使用既有优化库，只修正视距键并增加运行时断言。不改硬件设计、不启用FSR/CNN、不修改SD默认入口。

## 为什么 Mali 的数值尚不足以判定 GPU 上限

此前 Mali 的 Far=7.82 FPS、正确Tiny=40.76 FPS，均是原版世界静止短测。Tiny的CPU进程平均约0.986核，交换函数占配对窗口约41.03%。后者同时含GPU等待、PBuffer读回和X11复制，不能直接解释成纯复制比例或GPU着色耗时。其余时间还含Java游戏/显示列表构建、JNI、GL4ES桌面API翻译、驱动提交与帧率策略，尚未做逐阶段归因。

该Mali路线为 Java/LWJGL→GL4ES→厂商GLES1→Mali→PBuffer读回→X11。它已证明真实GPU渲染，但不是适配完成的最短显示通路；也没有验证GPU时钟/PP利用率或证明硬件已满载。应先把这几个环节分开计量，再决定优化驱动、批次还是显示交接，不能把单轮FPS直接当硬件极限。

PL当前路线为 Java/LWJGL→私有libGL→A53几何前端→PL RasterIX双纹理/深度/混合→帧桥与LCD。虽然像素在FPGA，顶点变换/裁剪/三角形准备仍有CPU工作。两条路线还存在精度、后端兼容实现与呈现路径的差别，单次FPS不能充当纯GPU核性能对照。

## 本轮修正与验证

旧脚本写入renderDistance:3，原版1.2.5实际只读取viewDistance，已确认R75–R78实际Far。新R79/R80写入viewDistance:3，并在暖机、计数开始和结束直接读取游戏hu对象的字段，要求：viewDistance=3、fpsLimit=1、fancyGraphics=false、clouds=false、difficulty=0。

使用同一冻结超平坦存档，逐个校验11个源文件，60秒静止暖机后测约30秒。沿用同次PL状态读取的单调时钟与完成呈现计数，只统计已完成帧；截图在测量后取得SNP1不可变租约，不能用菜单循环计数代替游戏世界帧率。

二进制沿用已验收顺序绕过库8e89c36f…，prepared/queued/texture-dedup/batch-bypass均开启。Java双TMU位流14fd58da…由原控制器安全加载；每轮自动恢复原v23，并保留全部保护与失败记录。新运行器Windows逻辑与Linux实际锁/回滚九项检查均通过；实际板侧继续执行双纹理、显示列表、满条带、纹理局部更新和交换计数回归。

## 实测结果

回读归档、每轮压缩包及原导出块均已核对SHA-256；两轮独立运行验收通过。实际参数在暖机与计数两端均符合要求，硬件错误为零，玩家位置、朝向、Health=20、DeathTime=0及最终世界时间2279与Mali样本一致。

| 路线 / 轮次 | 实际视距 | 完成帧 / 窗口 | 平均FPS |
|---|---|---:|---:|
| PL / R79 | Tiny | 784 / 31.005475 s | **25.2859** |
| PL / R80 | Tiny | 785 / 30.001743 s | **26.1651** |
| PL / 两轮加权 | Tiny | 1,569 / 61.007218 s | **25.7183** |
| Mali GLES1 / 先前world-r3 | Tiny | 1,223 / 30.001780 s | **40.7642** |

因此，正确Tiny下PL已是约25–26FPS，不能再引用Far的4.89FPS称为Tiny表现。Mali本次应用链路的单轮读数约为PL两轮加权的1.585倍，但不是同批次交错ABBA或纯GPU核加速比；Mali统计PBuffer/X11完成交换，PL统计完成呈现，精度与后端路径也不同。

两轮PL采样累计CPU分别0.983/1.106核，去掉Compiler命名线程约0.913/0.903核；DMA完成等待约29.26%/29.57%。命令流分别25.08/25.22MiB/s，纹理STORE约6.82MiB/s。这些窗口略小于完成帧窗口，且存在并行工作，不能把CPU百分比与等待比例直接相加；它们说明仍有前端、命令搬运及同步开销，尚未单独定位纯PL像素核上限。

本轮每次48幅原生回归图与R77已验收图像比较，共36,864,000字节完全相同；游戏图像实际读回完整，两轮PL世界原始RGB565也相同。Mali/PL的世界图不作为逐字节等价证明，图中快捷栏混合和颜色存在差别，尚待单独核对后端精度与兼容语义。

## 其它视觉设置：并非全最低

以下是本轮继承的原选项加运行器明确改写后的配置；Mali Tiny使用相同设置。Fast不等于把所有视觉选项都关掉。

| 项目 | 本轮配置 |
|---|---|
| 视距 / 基础画质 | Tiny / Fast |
| 云 | 关闭 |
| 平滑光照 / AO | **开启，ao:true** |
| 粒子 | **全部，particles:0** |
| 行走晃动 | 开启，bobView:true |
| 高级OpenGL遮挡剔除 | 关闭，advancedOpengl:false |
| 红蓝立体 | 关闭 |
| 视场 / 亮度 | 默认视场，gamma:0 |
| 纹理 | 默认材质，保留完整256×256图集 |
| 后处理 | 最近邻显示；FSR/CNN关闭，未装光影包 |
| 帧率策略 | fpsLimit:1；原版lr字节码对应目标120FPS，**不是40FPS省电档** |
| 游戏环境 | 和平难度、静止超平坦场景 |

可另做真正最低配置的对照，例如ao:false、particles:2、bobView:false；当前没有执行该轮，也不预先承诺提升。静止空地中粒子及晃动可能没有实际负载，降低这些选项不一定显著提高当前样本帧率。高级OpenGL是遮挡剔除开关，需验证对应接口后再尝试，并非单纯画质开关。

## 验收修正与最终状态

旧独立验证器要求游戏日志必须出现GPU条带满溢，这在Far大批次下成立，却不适用于Tiny的小批次。R79首次独立验证因此拒绝，原始板端记录及归档均保留。新分支只对已固定正确Tiny、运行时字段匹配的轮次允许游戏满溢次数为零；仍要求独立65,536顶点压力探针两种路径实际满溢，每模式6次，整帧及最终队列数量正确。没有取消硬件压力测试，也没有改写原始结果。[首次拒绝说明](../build/minecraft-java-125/tiny-r79/initial-verifier-rejection.json)保留。

两轮均由原控制器恢复原v23，GPU/POST状态空闲、帧号与错误计数清零、CNN配置保留，保护检查通过。Mali未遗留加载，证据传输锁已释放，SD未更新；当前没有游戏进程。R80私有部署保留为可重用实验候选，默认入口未提升为此配置。
