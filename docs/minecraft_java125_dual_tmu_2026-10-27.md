# 原版 Minecraft Java 1.2.5：真实双纹理、提交修复与世界测试

> 2026-10-28 配置更正：历史脚本写入了 1.2.5 不读取的 `renderDistance` 键，本文的 Tiny 标注须按归档 `viewDistance` 复核；已确认 R75–R78 实际为 Far。原始计数及同组对照不重写，详见 [Mali 试验及视距核查](MALI_JAVA125_2026-10-28.md)。

2026-10-27。**R23 已让未修改的 Minecraft Java 1.2.5 通过原版菜单创建并进入超平坦世界。** 400×240、Tiny/Fast、关闭云的初次活动世界区间，10.025 秒完成 61 个 GPU 新帧，约 **6.085 FPS**。R21 的双纹理与本次世界证据分别保存。

## 已完成的链路

原版 Java / LWJGL → ARM 游戏逻辑、固定功能顶点处理及显示列表 → DMA 命令 → FPGA 双纹理、光栅化、深度与混合 → 显示桥 → 800×480 LCD。

原版客户端 JAR SHA-1 保持 `4a2fac7504182a97dcbcd7560c6392d7c8139928`。源渲染为 400×240，两路纹理均保留完整 256×256、双线性和 mipmap。本轮验证固定 nearest 呈现，未进行 FSR 画质或风格化性能验收。

后续 R25–R28 完成同一冻结世界四轮交叉对照：相邻纹理页合并后，**6.879 → 7.480 FPS，+8.73%**，纹理事务减少 96.67%，仍未达到流畅运行。原始 NBT 核对玩家位置、朝向和最终世界时间相同。见[纹理事务优化、对比图和后续瓶颈](minecraft_java125_texture_batch_2026-10-27.md)。

## 纹理队列及完成语义

之前的 `DeviceUploadList` 在约 4 MiB 暂存队列满后返回失败，日志持续出现页分配失败；`glFlush/glFinish` 为空实现。新私有库在队列满前等待旧工作与上传线程、排空已存页，再继续接收纹理，避免因为有限队列而遗漏上传。设备写入失败会终止该提交，保留错误。

`glFlush` 提交不换页的 IF 缓冲写回；`glFinish` 额外等待工作线程、上传线程及 DMA 完成。提交末尾附加 NOP，让真实 CommandParser 在前序光栅化与 framebuffer 操作结束后才能接收屏障后续命令。

R19/R20 实测：

- 三次清屏后立即在 DDR 核验完整后缓冲，共 **288,000 像素**；`glFinish` 没有增加显示帧号。
- 一次上传 **40 张完整 256×256 纹理，共 5 MiB RGB565**，超过 4 MiB 暂存预算，实际触发自动排空。
- 40 个纹理色块回读正确，原版菜单日志中的页分配失败和 `glFlush not implemented` 记录消失。
- 显示列表九组、完整纹理、原始 Mojang、连续换页和正常回退继续通过。

R18 首次色块探针使用无尺寸 `GL_RGBA`，驱动选用 RGBA4444 存储，和探针按 RGB565 设置的误差预期不一致。失败证据保留；R19 显式选择无尺寸 `GL_RGB` 对应的 RGB565 后通过，未降低阈值或忽略错误。

## Java 能力路径的核对

完整检查注册表后确认，原驱动的 **34 个 ARB 多纹理入口已经齐全**，没有必要重复添加。R20 通过真实 LWJGL 调用验证 `GL_ARB_multitexture=true`、`OpenGL13=false`，unit0 调用和越界拒绝有效。

原版 `es.class` 自带 ARB 分支。R21 在真实两个硬件单元上再次通过 Java ARB 调用、独立绑定和非法 unit2 拒绝。**不需要把版本字符串改成 OpenGL 1.3。** 本项目仍没有完成全套 GL13 实现或认证。

双单元私有库还修复了一个原有查询问题：`GL_CURRENT_TEXTURE_COORDS` 原先固定返回 unit0，现在按当前活动单元返回相应坐标；纹理矩阵也分别核验。

## 性能判断及下一步

当前只是跑通世界，**6 FPS 还达不到流畅演示**。本轮没有在世界中启用 FSR，也没有加入 CNN。LCD 扫描频率不能代替新游戏帧率；完整 GL13、全部原版特效及完整游戏兼容性也没有通过认证。日志仍有 `GL_CLAMP` 以 `GL_CLAMP_TO_EDGE` 模拟的提示，后续需专门核对视觉边缘。

| 活动世界原始量 | 结果 | 能说明什么 |
|---|---:|---|
| GPU 实际完成新帧 | 61 / 10.025 秒 | 初次世界约 6.085 FPS |
| 命令入口 32 位拍数增量 | 63,971,188 | 包含入口上所有协议/载荷，不能全算成几何 |
| 平均入口数据/完成帧 | 4,194,832 字节，约 4.0005 MiB | 值得按几何、纹理及协议分类统计 |
| `gpu_busy_cycles` 增量 | 136,490,055 | 100 MHz 下占该区间 13.615% |

`perfBusy` 在 RTL 中定义为 **CommandParser 的 `state != COMMAND_IN`**，因此上表比例不是整块 GPU 利用率。不能据此直接断言 86% 的时间被 CPU 浪费，也不能预测单独加快某个 IP 后的 FPS。本轮只读核对过实际 DMA 驱动：传入长度会原样提交，最小传输为 64 字节，尚未证明存在每帧固定 4 MiB 填充。

后续优先级为：

1. 复用保存的 `rixjava-r23` 世界，在相同位置做可重复的较长采样，记录帧间隔、各线程 CPU、纹理字节与次数、几何提交字节、DMA 等待及显示等待。
2. 根据分类数据减少显示列表重放中的重复顶点处理、状态设置或重复纹理上传。保持原版 JAR、两路采样和完整纹理，对照实际像素与新帧数，不能以跳过渲染换取更高计数。
3. 源渲染稳定后再比较最近邻与 FPGA FSR 的完整输出 FPS/画质。Java 双 TMU 配置中的 CNN 当前缺席；若要恢复网络风格迁移，需重新做资源分配和整机时序，而不能仅打开软件开关。

现有位流 LUT 93%、DSP 91.7%，继续复制运算单元空间有限。当前更适合先量化并减少软件前端与传输成本。已验证 v23 仍用于其他游戏演示；这轮没有把低帧率 Java 原型替换为 SD 默认入口。
