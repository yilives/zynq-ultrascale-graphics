# CNN / FSR 的 BRAM 回收方案

实现进展：[r1](CNN_INPLACE_R1_2026-11-01.md)已通过 RTL、AXI、功能网表、OOC、完整整机路由/配置审计及 [临时上板回归](CNN_INPLACE_R1_BOARD_2026-11-01.md)。**候选整机 CNN 为 28.5 BRAM，整机总计 189.5，实际回收 26.5 Tile，DSP 仍为 325；核心实测 462,816 周期。** 独立 OOC 的新核为 33 Tile，不能与整机混算。36 帧固定输出和 Neverball→CNN→LCD 短测通过；现已恢复原位流和清晰菜单，未设为默认。

以下保留 2026-11-01 实现前的原始分析。当时已完成算法验证，尚未实现 RTL 或新综合；216/216 指冻结的原 v23。下文 20–25 Tile 等数字是当时估算，实际已实现结果以上方 r1 为准。FSR 行缓存等其他方案仍未实现。

最新选择：用户已决定保留原有三层 8 通道网络，见 [CNN 当前主线](CNN_CURRENT_PROFILE.md)。下文更宽/更多层网络仅用于解释性能取舍，当前不实施。

## 优先方案：一个整帧库＋两行暂存

现有 CNN 用两个 160×96×8 INT8 整帧特征库交替读写，共 245,760 字节，实际核心为 55 BRAM Tile。3×3 卷积按行扫描时，旧输入行 r 的最后一批使用者在输出行 r+1；完成这一输出行后，就能用新结果覆盖旧行 r。

候选调度：

1. 保留一个整帧库，计算当前行，把量化结果放进两行循环暂存。
2. 完成行 y 的全部窗口读取后，把已算出的输出行 y−1 写回整帧库。
3. 最后一行计算完，依次处理最后的写回；整层写回结束才启动下一层。

这样不改卷积、复制边界、舍入、ReLU、饱和或权重，完整保留三层计算，不增加特征往返 DDR 的流量。

| 项目 | 当前双整帧库 | 原地写回候选 |
|---|---:|---:|
| 逻辑特征存储 | 245,760 字节 | **125,440 字节** |
| 变化 | — | 减少 120,320 字节，约 49% |
| 实际 BRAM | 55 Tile | **工程目标约 30–35 Tile，待综合** |
| 预计释放 | — | **约 20–25 Tile，尚未实现** |
| 额外数据搬运 | 无行复制阶段 | 三层共 46,080 个向量写回周期 |

按 100 MHz，每行复制所增周期合计约 **0.461 ms**，另有逐行流水排空和新控制开销；不能将其当作新核心的已测延迟。当前核心约 4.15 ms，可先将约 4.6–5.0 ms 作为设计估算区间，仍需 RTL 仿真和综合确认。这些都不是包括上传、融合、FSR、呈现的端到端帧率。

本方案保持原 64 路 MAC 复用。新增写回控制和选择器会消耗逻辑，仍需验证 100 MHz、BRAM 推断和完整工程布局布线。不能只在 Python 中删掉数组就宣称完成硬件优化。

### 已完成的验证

[算法验证脚本](../scripts/check_cnn_inplace_storage.py)与现有独立 INT8 全帧参考比较：

- 36 张历史真实输入 × 动漫/油画两套权重，共 72 个真实输入用例。
- 两套真实权重及一套极值压力权重，各测 1×1、单行、单列、2×2、3×3、小尺寸和 160×96，共 21 个边界/随机用例。
- **93 个用例、279 个层输出逐值一致，差异均为 0。** 压力测试覆盖负输入、正负大偏置、移位 0/1/9/20 和饱和。
- 故意在计算完一行后立即覆盖同一行的负对照，最终出现 **85 个通道值差异**，验证器能发现错误的提前覆盖。

完整记录：[inplace-schedule.json](../report/neural-style/bram-reclaim-20261101/inplace-schedule.json)。这是存储调度正确性验证，不是画风改进、RTL 周期精确仿真或 FPGA 容量验收。Python 中的参考结果和向量化临时数组也不是硬件存储分配报告。

若以后采用膨胀卷积，写回延迟必须随采样半径增加；例如半径 3 不能继续只延迟一行，通常需要保留四行待写结果。这一扩展本轮未验证。

### 对更宽网络的意义

16 通道采用“一个整帧＋两行”的逻辑特征容量为 **250,880 字节**，接近当前 8 通道双整帧的 245,760 字节。因此不一定要先再找 55 块 BRAM 才能研究加宽；可先重构复用方式。

但通道加宽后卷积工作量显著增加。保持 64 MAC 就需要更多时间，系数容量、分块调度和模型格式也要更新；不能由存储大小相近推导出 16 通道网络能保持当前速度、符合画质要求或整机一定装得下。

## 性能预算：省存储与扩网络分别计算

**保持现有 8 通道模型、只改存储，预计核心性能代价较小；如果再扩成 16 通道或更多层，就必须重新核算吞吐。** 省去的是一个整帧副本，64 路 MAC 和约 100 MHz 时钟保留，特征仍在片上；本方案没有把卷积的每个采样都转移到 DDR。

以下按 160×96、64 MAC、100 MHz、8×8 通道块调度估算。三层 8 通道每像素发出 27 个 tap；六层 8 通道为 54；三层 16 通道是 `9×(2+4+2)=72`。16 通道的首尾层也按 8 通道块补齐，尚未采用专门针对 RGB 的最优打包。控制、行复制、排空和更宽特征访问需要另外计入。

| 候选 | CNN 核心时间 | 若串行加现有 FSR 核心约 8.2 ms | 距 60 FPS 的 16.67 ms 还剩 |
|---|---:|---:|---:|
| 现有三层 8 通道，双整帧 | 4.147 ms，既有周期 | 12.35 ms | 约 4.32 ms |
| 同模型原地写回 | **4.6–5.0 ms，估算** | **12.8–13.2 ms** | **约 3.47–3.87 ms** |
| 六层 8 通道原地复用 | 9–10 ms，估算 | 17.2–18.2 ms | 已超出串行预算 |
| 三层 16 通道、64 MAC 分时 | **12–13 ms，估算** | **20.2–21.2 ms** | **已超出串行预算** |

这些和是串行方案的计算预算，不是已实现的 CNN＋FSR 链路。跨帧流水能够使吞吐受最慢独立阶段限制，而不是把所有核心时间相加；但需要独立缓冲、同帧标签及真正的重叠执行，当前尚未接入。分时共用同一 BRAM 池又会限制这种重叠。因此表格不能排除所有并行设计，也不能据此承诺某个整机 FPS。

现有 FSR 的约 8.2 ms 对应 **400×240→800×480**；CNN 输出是 **160×96**，不能直接交给这个固定尺寸内核。需要先在 400×240 域做同帧风格残差融合，或重新生成支持另一输入尺寸的 FSR，并重新验证画质和耗时。融合与搬运都不在上表内。

### 历史实测说明真正的开销

同结构 CNN 的 [v4 实板记录](CLASSICUBE_STYLE_EXPLORATION_V4_2026-10-22.md)中，固定张量的一整次推理约 **12.38 ms**：输入 PIO 约 **1.39 ms**，核心约 **4.15 ms**，输出 PIO 约 **6.84 ms**。真实 MC 会话另有 ARM 融合约 **8.9 ms**、显示写回约 **8.4 ms**，以及缩图和前台等帧；后台快照读取与前台重叠，不能将全部累计计时相加。

该历史配置没有 FSR：组合 ABBA 风格输出约 **26.25 FPS**，两风格长测分别约 **25.25/25.82 FPS**。这些不是当前菜单串入 CNN 的新测量，也不能当成原版 Java 的帧率。假设只把新增约 0.45–0.85 ms 完全串行地加到历史 26.25 FPS 上，算术敏感性约为 25.7–25.9 FPS；这是解释额外写回量级的假设，不是新方案的帧率预测。

因此首轮应保持模型宽度，验证省 BRAM 的实际代价，再优先消除 PIO 回读、ARM 全帧融合及显示往返。若要增强模型，先研究不增加 tap 数的感受野扩展，或低分辨率瓶颈层；直接全程加宽、同时沿用所有旧搬运阶段，不应以稳定 60 FPS 为可交付承诺。可先针对 ClassiCube 的最终神经显示争取稳定 30 FPS；Java 还受到自身 ARM 源渲染帧率限制，需要分开验收。

逐窗口交错写回有望隐藏部分行复制，但必须验证最后一次读取与 RAM 读写碰撞，目前未纳入节省时间。现有驱动的预期周期和新核心能力标识也需要同步更新，不能沿用旧 414,738 周期断言验收新调度。

[可重算时间预算](../report/neural-style/bram-reclaim-20261101/timing-budget.json)与[预算脚本](../scripts/estimate_cnn_reclaim_timing.py)绑定历史记录哈希；本轮未做新 RTL 综合或开发板性能测试。

## 第二方案：FSR 整帧输入缓存改行缓存

已路由 FSR 的 78 BRAM Tile 可按层级报告拆分如下：

| 用途 | BRAM Tile |
|---|---:|
| 整帧 RGB565 输入缓存，按顶层减去子模块得到 | **64** |
| RCAS 行存储及其子模块 | 9.5 |
| EASU→RCAS 像素 FIFO | 2.5 |
| 输出 FIFO | 1 |
| AXI 适配缓冲 | 1 |

源代码 `input_cache[4][240][100]` 逻辑容量 192,000 字节。它不是全部算法必须同时保留的工作集：EASU 需要的窗口跨四行，400 像素宽的四行 RGB565 只有 3,200 字节；增加一行预取则为 4,000 字节。考虑分银行、端口、突发预取和映射后，**可将释放约 50–60 BRAM Tile 作为架构探索目标，尚未实现或综合**。

改动比 CNN 原地写回更大：当前 LOAD 完整缓存一帧，COMPUTE 不再读取源 DDR；行缓存方案需要边读 DDR 边计算，还须保证该源帧在最后一次使用前不被游戏或下一次快照覆盖。必须重做输入预取、标签/所有权保持、背压和 AXI 完成条件，并验证 EASU/RCAS 的启动间隔与 200 MHz 时序。理想情况下每个源像素只读一次，源数据总量不必增加；这不是对真实带宽和帧率的保证。

综合日志另显示，输入缓存因时序要求被重新映射为深 BRAM 结构。也值得先检查能否用更紧凑的映射保住 200 MHz，但不能直接强制省面积后沿用原时序验收。当前 64 块的实际占用以路由报告为准，不能用 192,000 字节除以 BRAM 容量替代。

## 其他可选办法

| 方法 | 回收潜力或代价 | 采用建议 |
|---|---|---|
| 中间特征放 DDR，BRAM 留行/分块缓存 | 两份 8 通道中间特征各写读一次，理论约 0.492 MB/帧，60 FPS 约 29.5 MB/s；未计输入输出、协议、冗余读取和争用。逐 tap 直接读 DDR 会大得多 | 可扩展，但需要新增数据通路，先评估现有互联余量 |
| CNN 与 FSR 分时共用同一物理存储池 | 二者逻辑容量相加 437,760 字节，最大值 245,760 字节；理论差 192,000 字节，约 42 个 BRAM36 容量 | 需要统一存储控制、端口调度及跨时钟处理；会限制跨帧重叠。现有独立 IP 不会自动共享 BRAM |
| 单独构建无 FSR 的 CNN 实验配置 | 现有 FSR 占 78 BRAM、173 DSP；Java 已有无 FSR 独立分支提供实际资源对照 | 改造最快，但失去 PL FSR，不作为本轮默认选择，保留全部旧代码 |
| 缩小 RasterIX 颜色/深度/纹理缓存 | 会增加条带次数或外存访问，可能影响当前游戏帧率 | 暂不优先 |
| 把大特征库改成 LUTRAM | 245,760 字节约 197 万 bit，理论也需约 30,720 个 64-bit LUTRAM 单元，远超当前 LUT 余量 | 不适合用于整体替换；小 FIFO 可另行评估 |

回收潜力不是各项可直接相加的收益。同一缓存被重构或共享后，不能再重复计算其节省量。运行时关闭 FSR/CNN 也不会释放物理 BRAM，必须重新综合独立配置。

## 推荐顺序与当前边界

**保持原网络的 CNN 原地写回已完成 RTL、仿真/综合、原模型逐值对照、完整工程路由及配置数据审计。后续继续验证相同网络下的传输和融合。** 现有 FSR 保留，中间特征未增加 DDR 流量，通道和层数未扩大。

若该路线仍不够，下一步研究 FSR 输入行缓存；这是更大的容量来源。回收存储只能解决容量，不能自动解决不满意的风格目标、泛化和计算吞吐。两种已被否决的教师不会因为换存储而重新变成可采用模型。
