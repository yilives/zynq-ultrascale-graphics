# AXU3EG：原版 Java 1.2.5 的 Mali 路线实测

2026-10-28。用户授权试验 Mali 渲染。全部在 RAM 内完成；SD、系统默认 GL 库和 PL v23 位流保持原样。本文区分 GPU 渲染帧、X11 呈现和 LCD 扫描，不将它们当成同一个计数。

## 已完成的底层接通

板上的 PS Mali 设备树最初为 disabled，内核未装 Mali 模块，但 headless/x11 用户态 r9p0 驱动已存在。本次从 Arm 官方 r9p0-01rel0 GPL 源码，应用 AMD rel-v2020.1 的 16 个补丁，针对当前实际 Linux 5.4 构建模块。加载前核对实时 `/proc/config.gz` 与内核 `.notes`，不只比对版本字符串。

- 内核 notes SHA-256：`61b2e5d9f52fb4afa44160141a432c6b2204a1da0d4401a960c25d33a559f4d3`。
- 模块与设备树通过独立 configfs overlay 临时启用，没有更改磁盘启动设备树。
- `/dev/mali` 正常打开；原生 GLES2 报告 `Mali-400 MP`。GPU 顶点 shader 执行矩阵变换和双纹理采样，400×240 的 96,000 像素与参考整帧完全一致。

原生 GL4ES 使用未修改的上游 `1891af323d4547487296e50ba5932bde65c7b345`，私有库 SHA-256 `788fce5147778aa318c46248ac1e8d8f0535cb41a68e1ba21d9e670b411cb05f`。没有改写上游源码、提交 PR 或替换系统库。GL4ES 的 1.5/2.1 字符串表示兼容层接口，不代表 Mali 硬件原生支持桌面 OpenGL。

## 首轮故障与接口选择

1. 窗口管理器将有装饰的 400×240 客户窗口压成 400×174，导致 66 行读回无效。无装饰窗口和正确画布大小修复后，三组双纹理整幅 RGBA 校验通过；Java LWJGL 的显示列表、四边形和 96,000 像素检查也通过。失败目录 compat-r1/r2/r3 原样保留；r2 是 BusyBox 不支持 cp -n 导致探针未复制，r3 仅 Java 窗口尺寸失败。
2. GLES2 的首次实际世界可以运行，但出现 1,750 次客户端 GL 错误。诊断 JNI 将错误定位到 glShadeModel：Mali 合并库导出了 GLES1 入口，GL4ES 将它误调用到 GLES2 上下文。**world-r1 的约 12.154 FPS 只作诊断，不能作为无错误的性能验收**。板端原记录 passed=true 仅覆盖该脚本原有断言，独立验收补充拒绝此轮，原证据不重写。
3. 改用 GL4ES 原有 GLES1 后端，符合 1.2.5 所需的旧固定管线接口。compat-r5 已通过三组双纹理整帧及 LWJGL 像素检查，保持 LIBGL_NOERROR=0、原始纹理和错误日志，不用屏蔽错误的方式达标。

## 历史视距标注更正

原版 1.2.5 的 hu 类读取 `viewDistance` 到字段 e，0/1/2/3 分别是 Far/Normal/Short/Tiny。此前自动脚本添加了 `renderDistance:3`，这个键被忽略；R75–R78 原选项中的 `viewDistance:0` 得以保留。故其 **实际视距为 Far，不是文档标注的 Tiny**。JAR 的反汇编和冻结原选项可独立核对。

旧组内开关对照的原始完成帧和窗口仍可复算，因为相同错误对两组一致；不能把这些值宣传为已测 Tiny。其余历史组也需按实际选项复核，原始 result.json 和历史图不改写。本次先做实际 Far，再单独做正确 Tiny；后者降低可见距离，不当成单纯架构加速。

## 游戏与测量方法

使用未修改的官方 1.2.5 客户端，SHA-256 `c1c3740a912ef523a8bd46605ab5708643498330140cba175c7ce6f177e468e1`。原始冻结超平坦存档 11 个文件逐项校验，复制到私有 HOME 后仅经原版 GUI 点击进入。和平、Fast、关闭云，400×240，保留完整纹理，LIBGL_SHRINK=0，不启用 CNN 或 FSR。

独立 LWJGL JNI 在真实 glXSwapBuffers 返回后记录累计帧和同一时钟域的单调时间，使用序列锁读稳定样本。单次 Display.update 使计数准确增加 1 的独立探针先通过。世界 60 秒静止暖机后测约 30 秒，结束后才申请渲染线程读回原始 RGBA，避免截图进入测量区间。保存进程 maps 与打开的 /dev/mali，排除 RasterIX、llvmpipe、swrast 回退。

当前采用 LIBGL_FB=3：Mali PBuffer 渲染完成后，GL4ES glFinish、读回并拷贝到 X11。因此计数含 GPU 工作与这条呈现路径的开销，**不是 PL/LCD 的实际显示 FPS，也不是零拷贝**。本轮不使用保持为零的 PL 帧计数推算 Mali 帧率。

独立回读校验通过，原始两份归档及每个文件均核对 SHA-256。两轮均确认运行时 `viewDistance` 字段、世界活动区间、Mali 设备与私有库映射；正常关闭后，玩家位置、朝向与冻结源一致，Health=20、DeathTime=0，最终世界时间均为2279。

Far 相比历史 RasterIX 顺序绕过约4.89 FPS更快，但本次只有单轮，后端、渲染精度和呈现路径也不同，**不是严密 ABBA 架构加速比**。Tiny 的40.76 FPS同时受减小视距影响，不能称为相同负载下提升8倍。当前没有稳定32/60Hz、真实USB键鼠、复杂地图、移动场景或长期稳定性结论。声音仍使用客户端 Silent Mode，JInput手柄库缺失不等同于LWJGL键鼠不可用；本次只验证了自动GUI输入。

## 对工程路线的意义

Mali 使用 PS 已有硬核完成旧 3D 管线，可避免 RasterIX 路线在 A53 上逐顶点变换、裁剪和生成三角形命令。ARM 仍执行 Java 游戏逻辑、显示列表构建和 API 翻译。两者不是已经实现的“半个 Mali 接半个 RasterIX”。

如果采用 Mali 作为游戏渲染器，下一阶段是 **Mali 完整帧 → 帧交接 → PL 低分辨率 CNN → PL 超分 → LCD/DP**。当前尚未接通该实时桥；不能因 GPU 图像读回成功就说 LCD、FSR 或神经风格化已经启用。首先用有明确所有权、帧号和 fence 的拷贝通路，再验证 DMA-BUF/格式兼容与零拷贝。

现有 v23 中 RasterIX 占据的逻辑不会因运行 Mali 自动释放；是否重综合成 Mali+PL 后处理配置、可省多少资源及新增缓存成本，必须另做实现报告。原 RasterIX 路线继续保留，适合作为自研 FPGA 渲染/几何加速的研究与对照。


同日已完成[正确 Tiny 的 RasterIX 复测](JAVA125_PL_TINY_2026-10-28.md)：两轮25.29/26.17 FPS，加权25.72 FPS，主体设置与本次Mali Tiny一致；仍非交错ABBA或纯GPU核比较。平滑光照开启、粒子全部、晃动开启，并非全最低。后续再实现 Mali→PL 帧交接并计量回读、格式转换、搬运与帧龄，之后增加低分辨率 CNN/FSR。当前 GL4ES→X11 路径有已测复制成本，值得直接接后处理，但优化或零拷贝收益尚未验收。
