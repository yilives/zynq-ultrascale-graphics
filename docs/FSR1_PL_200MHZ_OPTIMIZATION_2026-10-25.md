# FPGA FSR 200 MHz 与扫描缓存优化实验

状态：v22 和 v23 均完成整机布局布线、独立工程审计、实际 RAM 加载、完整静态图／LCD 核验及同场景 ABBA 对照。当前板上为 v23；相同 a5 预取程序在 20 秒窗口内的新输出由 v19 的 **36.83 FPS** 提高到 v22 的 **44.37 FPS**、v23 的 **47.83 FPS**。最新 LOAD 后提前请求调度的两轮各 120 秒长测，视距 32 为 **57.09 FPS**、视距 16 为 **60.11 FPS**，后者有一次确认间隔略超门槛，严格稳定 60 判据仍未通过。不同时间窗和视距的结果分别列出。

目标是在 MC 400×240 → LCD 800×480、64³ 世界、视距 32、style0 条件下，尝试达到稳定 60 个新输出帧／秒。当前 LCD 的像素时钟为 200/6 MHz，水平总长 1056、垂直总长 525，物理刷新率约 60.125 Hz。超过此值的内部处理吞吐量不能直接成为更多 LCD 显示帧。

## 扫描缓存分组

原缩放器用单一分布式存储阵列异步读取相邻两行、两列。按行和列奇偶分组后，各组只需一个读地址，减少读端口造成的存储复制。像素运算、输出延迟、就绪、帧切换、欠载和丢帧控制保持相同。

| 单独缩放器 OOC 综合 | LUT | 其中分布式存储 LUT | BRAM | DSP |
|---|---:|---:|---:|---:|
| 已接受的 v8 原版 | 8,810 | 5,600 | 0 | 0 |
| 四行分组实验 | 5,727 | 2,912 | 0 | 0 |
| 行与奇偶列分组（选用） | 3,978 | 1,568 | 0 | 0 |

选用方案独立综合少 4,832 LUT，约 54.85%。这是相同条件下的模块面积比较。报告在 `report/fsr-pl/scaler-bank-area/`；整机最终资源另见下表。

v22 实际使用 `build/fsr-pl/video-v23-paritybank/video/`，其中 `v23` 是视频独立实验编号。该模块与已接受的 v8 参考共同进入 XSim，逐周期比较 RGB、同步信号、ready、drop 和 underflow_count。两个缓存实验均通过视频帧切换、POST、原生全屏扫描和两项预期失败对照，共五项检查。源文件、模拟克隆及实际工具日志均由最终接受脚本核对。

## 200 MHz FSR

候选 `fixed-v22-bankedscan` 与当前 v23 保留完整 EASU12／RCAS5 定点运算、四路输入缓存、64 字预填充写突发和最终 AXI B 完成约束。只缩窄有明确边界的内部参数：输出 x 0…799、y 0…479、方向权重 1／3／9。HLS 用 5 ns 周期重新调度，FSR 接入已有 MIG UI 200 MHz 时钟及其本地同步复位。PS AXI 通路与 RasterIX 保持 100 MHz，LCD 时序保持原值。ARM 负责游戏逻辑、顶点前端及帧所有权调度，运行时不执行 FSR 像素计算。

控制 SmartConnect 增加第二时钟输入，负责 PS AXI-Lite 到 FSR 的跨时钟访问；DDR SmartConnect 已有该 UI 时钟。完整工程必须通过资源、时序、CDC 与总线偏斜检查，不使用新的全局时钟假路径。

## DDR 读取定位

v19 原始证据中，三张静态黄金图的 LOAD 分别为 1,108、1,109、1,106 µs；MC 候选运行时按帧加权平均为 5,344.159 µs。静态测试没有游戏，POST 保持模式 1；MC FSR 测试使用模式 2 的原生扫描。因此两者不能直接归因于某一个硬件单元，但提示需要复测 DDR 争用，而不能只按 FSR 时钟翻倍预测 FPS。原始证据为 `report/postproc_fsr_prefetch_v19_11f7_evidence.bin`。

本轮已在原 v19 位流上完成额外离线对照：相同 scratch 输入、无游戏、扫描模式按 1／514／514／1 顺序，每组五次，另有一次预热。21 帧、8,064,000 像素与黄金图一致，前后 GPU／POST 状态一致。模式 1 的十次 LOAD 平均 **5,583.7 µs**，模式 514 为 **5,271.5 µs**；计算平均分别为 15,457.4、15,444.1 µs。新结果说明长 LOAD 也会在无游戏的显示状态下出现，不能把历史差异全归因于 MC 或两种扫描模式。仅十次样本且使用 CPU 时间测量，不是 DDR 周期计数或实时游戏 FPS。原始串口记录 `report/board_serial/fsr_load_probe_v19.log`，独立重算记录 `report/fsr-pl/fixed-v19-narrowtap/load-contention-diagnostic.json`。

代码与 RTL 对照进一步定位：普通扫描原来会将行缓存的 `ready` 背压传入 DDR R 通道，直到当前突发完成；CNN 扫描原有的 256×128 位 BRAM 则先收齐一段突发。v23 让全部模式复用这块现有 BRAM，避免下游停顿占住读响应。私有源位于 `build/fsr-pl/video-v24-burstcache/video/`，原公共 RTL 保持不变。五项视频回归通过；额外测试覆盖 96,000／384,000／15,360 像素、ISSUE／READ／STREAM 取消及 RRESP、提前／延后 RLAST 错误，共九项，要求正确排空、无错误像素发布。原版负对照实际命中 `READ_BURST_HELD_BY_DOWNSTREAM_READY`。原版与修复版独立 OOC 综合分别为 385／384 LUT，均使用 2 个 BRAM Tile、0 DSP，报告位于 `report/fsr-pl/reader-buffer-area/`。实机同调度 LOAD 从 v22 约 3.61 ms 降至 v23 约 0.79 ms，计算耗时均约 8.20 ms。
