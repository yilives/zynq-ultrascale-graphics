# ClassiCube 顶点读取与 CPU 开销优化

本轮为 ClassiCube 增加独立 RasterIX GL 库，优化 ARM 上的顶点读取，保持原生游戏二进制、素材、400×240 渲染和 800×480 LCD 输出不变。**主要收益是节省 CPU，实际显示帧率基本持平。**

## 实测与口径

同一原生游戏、同一地图种子 314159、64³ 地形、异步提交及 120 FPS CPU 上限，每轮运行 62 秒、预热 2 秒，以原生硬件 `presented` 计数测量后约 60 秒。两种视距都按旧库、新库、新库、旧库顺序交叉测试：

| 项目 | 旧库 | 专用库 |
| --- | ---: | ---: |
| 32 格视距，实际 LCD FPS | 57.53 | 57.57 |
| 64 格视距，实际 LCD FPS | 55.88 | 55.99 |
| 32 格视距，前台绘制平均耗时 | 约 7.0 ms | 约 3.1 ms |
| 64 格视距，进程累计 CPU 用时 | 97.97 秒 | 79.61 秒 |

前台绘制耗时降低约 56%，高视距进程总 CPU 用时降低 **18.7%**。累计 CPU 时间可超过墙钟时间，因为包含多个线程；统计覆盖启动器及其已回收子进程，包含相同的启动和冻结取帧阶段。它不是单帧 GPU 完成耗时，也不是整机功耗测量。

两种库的实际显示帧率差异很小，应视为持平。前台绘制省下的时间主要转为等待后台流水；CPU 提交速度不能当作 LCD 帧率。原始交叉数据见 `report/classicube/vertex-optimization/matrix.json`、`far.json` 和逐次游戏日志。平地约 60 FPS。

## 实现

`ports/classicube/PackedVertexReader.hpp` 为常用数组格式提供一次检查后的读取路径：float3 位置、ubyte4 RGBA 颜色、可选 float2 纹理坐标。它保留数组偏移、显式或紧密步长、常量法线、点尺寸及禁用属性的语义。纹理数组禁用时不读取其指针或步长；其他格式和索引绘制继续使用通用路径。

归一化颜色仍采用原来的 `1.0f/255.0f`，没有使用 fast-math。读取使用普通 VBO 进程内存，不直接访问正在渲染的 Device 映射帧缓冲。获取顶点的缓存只在需要的索引绘制分支初始化。后台顶点变换、裁剪、三角形设置和 FPGA 像素流水本轮未修改。

新库只在 ClassiCube 的校验包内解压到 RAM，通过明确的 SDL GL 驱动路径及库路径加载。其他游戏仍使用原共享库。诊断对照入口：

```sh
rix-classicube
rix-classicube --vertex-fetch legacy
rix-classicube --vertex-fetch generic
```

默认 `packed`；`legacy` 加载原共享库，`generic` 在专用库内走通用顶点读取。以上均保持正常键鼠游戏，默认持续运行至菜单退出。`--seconds`、`--autoplay`、`--capture` 仅用于自动诊断。

## 等价性与交付验证

主机 ASan/UBSan 检查覆盖 12,288 个顶点与 84 个回退用例，包括独立/交错数组、步长、非零偏移、颜色边界以及未配置的禁用纹理数组。最终修正版上板又对 1,157 万个顶点的全部有效字段逐位比较，未发现差异。

图像取证保留原 OpenGL 回读诊断，同时在游戏明确暂停提交、CPU/DMA/GPU 队列排空后读取硬件实际完成的 PS 源槽，验证帧号、源地址、命令计数和双次数据稳定，再与独立 LCD 样本比较。这里没有将 OpenGL 假定的 front 指针当作物理显示源，也没有让运行中的 CNN 绕过快照租约。

最终交付验证由 `scripts/record_classicube_vertex.py` 汇总到 `report/classicube/vertex-optimization/acceptance.json`，**44/44 项通过**。最终包补齐禁用纹理步长条件检查后，再次验证默认及高视距路线、通用和索引回退、真实 X11/SDL 键鼠输入、菜单存档、八个移动视角取帧以及正常重启后的 RAM 恢复。最终包的实际呈现源共核验 126,000 个独立 LCD 样本，全部一致；包含交叉对照共 174,000 个样本。菜单存档的 65,536 个方块在重载及重启后逐项哈希一致。

最终包重复长测为默认视距 **57.60 FPS**、64 格视距 **55.82 FPS**，平地 **60.16 FPS**；高视距进程 CPU 用时为 79.66 秒，确认约 18.7% 的节省。交叉研究使用的 v16 候选包与最终 v17 包分别保留，报告不会混用包哈希。原生游戏、素材、原共享图形库、BOOT/设备树及 31 个神经网络文件均通过哈希核对，GPU 各错误计数为零。

实体 USB 键鼠尚未连接，自动输入检查不能替代 DPI、按键手感和端到端延迟测试。

## 构建与继续优化

完整构建入口仍为 `build.ps1 -Action classicube`。独立库构建脚本为 `scripts/build_classicube_graphics.sh`；准备器先在单独目录生成基础库，再只写入实际变化的文件，避免每次把已修改头文件恢复后又重写而触发无关重编译。

在 WSL 完成准备后，可运行 `python3 scripts/check_classicube_packed_reader.py` 重复主机等价检查。包内包含 RasterIX 许可证、源文件哈希和专用库修改记录。

后续若要继续提高复杂场景 FPS，需要分别测量后台顶点变换、裁剪、三角形设置、DMA 和显示等待，再决定做 ARM 向量化或把更多几何处理交给 FPGA。本轮结果只证明前台读取与总 CPU 开销下降，不能据此宣称整个渲染流水已加速。
