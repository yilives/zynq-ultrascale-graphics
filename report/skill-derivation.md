# 技能包提炼过程

> 对应指南 3.3.5.3：**「技能包的提炼过程：从哪些失败或观察中总结、如何验证有效、边界如何确定」**
>
> 技能包主体见 `skill/README.md`（14 条，P1–P14）。本文说明这 14 条是**怎么来的**、
> **怎么确认它们有效**、以及**每条在什么情况下不成立**。

---

## 一、提炼方法：从 451 次工具失败里逆向筛

技能包不是「想出来的经验」，是从**原始协作记录**里筛出来的。

### 1.1 数据来源

| 项 | 数量 |
|---|---|
| Codex 会话文件 | 358 MB JSONL，86,748 条事件 |
| 工具失败输出 | **451 次** |
| 助手自我纠错（含「误判/撤回/不采用/不足以」等 19 个关键词） | **166 处** |
| 用户直接质疑模型的记录 | **8 处** |

### 1.2 四步筛选

```
① 机械抽取
   脚本 scripts/_extract_codex_collab.py 按 role / 关键词 / 工具退出码抽取
   → 451 失败 + 166 纠错

② 归因分类
   把 451 次失败按「根因」聚类，得到 4 类：
   面积类（P1/P2/P3）· 接口类（P4/P5/P6）· 口径类（P7–P10）· 流程类（P11–P14）

③ 反向验证（这一步最关键）
   每条候选都要回答：**「如果这条规则成立，项目里应该有一次它被违反的事故」**
   找不到事故的，不进技能包。
   例：「跨时钟域要用打包+握手」这条，对应 `rix_presenter` 首版因多比特同时跳变
        导致偶发错帧的真实记录。

④ 抽掉题目特异性
   把「本项目的具体数字」换成「可判定的条件」。
   例：「91,645 LUT 装不下」→「OOC 面积不能直接相加，需乘 1.8–2.0 集成系数」
```

### 1.3 淘汰记录（为什么是 14 条而不是 30 条）

| 被淘汰的候选 | 淘汰原因 |
|---|---|
| 「Vivado 综合慢要多线程」 | 属常识，无本项目特有观察 |
| 「DDR4 校准要先等 locked」 | 太具体，只对本板 MIG 配置成立，不是通用规则 |
| 「用 `git` 管理 RTL」 | 无失败事故支撑，属个人偏好 |
| 「CNN 用 INT8 省资源」 | 缺量化对比实验，只有单点观察 |
| 「HLS 加 pipeline 提升吞吐」 | 是工具手册内容，不是踩坑 |

**只有「有事故、能定位、可判定」的才留下。**

## 二、14 条的来源与验证方式

每条都标了「来源事故」与「验证方式」。**验证方式是这条能否成立的关键。**

### 面积类

| 条目 | 来源事故 | 验证方式 |
|---|---|---|
| **P1** OOC 面积不能直接相加 | 预估 CNN 集成需 4,466 LUT，整机实增 **8,265**（1.89×），`place_design` 失败 | 对比 `final_opt_utilization.rpt` 与 `final_opt_utilization_hier.rpt` 的逐模块增量，确认既有 FSR/GPU/DDR4/互联全部跟着长 |
| **P2** HLS 面积重建有下限 | 27 轮从 374,209 压到 91,645（−75.5%），可用仅 32,510 | **反证法**：把变换/裁剪/法线矩阵全假设为零面积，剩余仍 46,058 > 32,510 |
| **P3** `place_design` 失败时无时序 | 同一报告 `WNS +0.741`（好看）但 `WHS −0.110`（违例）且布局未成功 | 检查报告中是否同时出现 `WNS` 与「布局失败」；三阶段报告对照 |

### 接口类

| 条目 | 来源事故 | 验证方式 |
|---|---|---|
| **P4** DMA 槽数 ≠ 并发数 | 8 槽但 `if(c->active) return -EBUSY`，每通道一笔在途 | 读 `rix_dma_proxy.c` 的 active 检查 + 用户态 `waitForDma()` 调用点 |
| **P5** 跨时钟域要打包+握手 | `rix_presenter` 首版多比特同时跳变 → 偶发错帧 | `report_cdc` 的 Multi-bit CDC 告警；且现象呈「大部分正常、几百分之一错」 |
| **P6** 复位异步置位同步释放 | 单复位驱动三域 → 上板偶发首帧错乱 | 每域独立 4 级 `ASYNC_REG` 链后复测；对 CLR 脚加 `false_path` |

### 口径类

| 条目 | 来源事故 | 验证方式 |
|---|---|---|
| **P7** 「利用率」计数器读错 | `perfBusy = state != COMMAND_IN` 被当成像素利用率（48.9–51.9%） | 读定义那一行源码，问「它排除了什么」 |
| **P8** 性能数字必须带口径 | 同项目 5 个「FPS」测的是 5 件不同的事 | 建表：57.09 / 44.35 / 40.76 / 25.72 / 60.125 各自含义 |
| **P9** 配置键写错整组实验作废 | 脚本写 `renderDistance`，游戏读 `viewDistance`，四轮 ABBA 全作废 | 从**游戏对象**读实际值，暖机/开始/结束各读一次必须一致 |
| **P10** 浮点重排改变结果 | MVP 预乘后 **47.08%** 字段逐位不同，最大 ULP 差 **1,144** | 逐位探针：真实夹具 + 每步舍入 float32 + 比 ULP |

### 流程类

| 条目 | 来源事故 | 验证方式 |
|---|---|---|
| **P11** 串口/句柄独占 | 启动器持状态设备句柄 → 内核拒绝卸驱动；COM11 被上位机占用 | 报 `Access denied` 时先查「谁占着」，不重试 |
| **P12** 不安全终止致整板不可用 | 强杀进程 → 隔离标记 → 该 `boot_id` 内拒绝一切新游戏 | 看隔离文件是否存在且 boot_id 匹配 |
| **P13** RAM 位流断电即失效 | 一切正常但断电回旧版本，且**无脚本校验** | 三个身份比对：RAM SHA / BOOT.BIN SHA / manifest |
| **P14** 验收脚本是假失败源 | `0x203` 被误判；单行汇总误当时间序列 | 拆「结构断言」与「值断言」分别跑；**必须配负对照** |

## 三、如何验证「技能包本身有效」

这是指南问的「如何验证有效」。我们用了三个手段：

### 3.1 负对照：证明检查器真的会报错

**最强的一条证据**：CNN 存储复用验证了 93 个用例、279 层输出零差异。
但「零差异」本身不说明验证器有效——**验证器可能永远返回通过**。

所以我们**故意提前覆盖同一行**，验证器抓到 **85 个通道值差异**。

**这才证明「零差异」是真结论，不是空声明。** 这条方法本身就是 P14。

### 3.2 失效条件：每条都写明「什么情况下不成立」

技能包最容易犯的错是**把特例当通则**。所以每条末尾都写「失效条件」：

| 条目 | 失效条件 |
|---|---|
| P1 | 若新增模块不引入新 AXI 主设备、不复用既有互联，集成系数会小很多 |
| P2 | 若目标器件余量在 10 万 LUT 以上，同样重构可能就收敛了 |
| P3 | 小规模模块（占用 < 10%）的布局前估计通常与布线后接近 |
| P4 | 若驱动改为多 in-flight 描述符队列，此条不成立 |
| P5 | 纯控制脉冲（单 bit 事件）用 2FF 即可 |
| P6 | 单一全局复位且全设计只有一个时钟时不需要多链 |
| P7 | 若计数器直接来自「有效字节数 / 时钟数」这类物理量，可直接用 |
| P8 | **无失效条件**（任何性能文档都成立） |
| P9 | **无失效条件** |
| P10 | 若下游全程 float64 且只做大小判断，ULP 差异可能可接受 |
| P11 | 需持续轮询的场景可以常驻，但结束路径必须关闭 |
| P12 | 纯只读操作不受此限 |
| P13 | 位流已写入 SD 且经冷启动验证时不适用 |
| P14 | **无失效条件**（任何自动验收都需负对照） |

**14 条里只有 3 条（P8 / P9 / P14）没有失效条件**——它们是真的通则。
其余 11 条都限定了适用范围，避免被当成万能规则。

### 3.3 可迁移性自检：换一个项目还成立吗

对每条问三个问题：

1. 这条规则**依赖本项目的具体数字**吗？（如「91,645」）→ 若是，改写成条件式
2. 这条规则**依赖本块板卡**吗？（如「AXU3EG 的 MIG 配置」）→ 若是，降级为观察，不进技能包
3. 这条规则**依赖本题目**吗？（如「图形渲染」）→ 若是，抽象到方法层

**通过这三问的才留下。** 例：P10（浮点重排）原本写成「MVP 矩阵预乘要小心」，
抽象后变成「任何浮点运算重排都要量化 ULP 影响」，换到信号处理项目一样成立。

## 五、技能包的边界（诚实说明）

**这份技能包不包含的内容，以及为什么：**

| 不含 | 原因 |
|---|---|
| PYNQ Overlay 加载范式 | 本作品**不使用 PYNQ**（自建 Linux 运行时），不编造未实践的内容 |
| AI Engine / Versal 相关 | 未使用该器件 |
| 高层次综合的通用调优技巧 | 属工具手册内容，非本项目踩坑 |
| 功耗测量方法 | 本项目未测功耗，无观察可总结 |

**技能包是派生物，不是权威源。** 若与源码冲突，以源码为准。
