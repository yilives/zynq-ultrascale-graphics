# `skill/` —— 可复用技能包

> 对应 AMD 赛道指南 3.3.5.2：技能包须含 `README.md`，说明每一项的**适用范围、使用方法与失效条件**，
> 并说明是从哪些失败或观察中总结得出。评价标准是**可复用性**。
>
> 本技能包主体是**踩坑清单**（指南四类之一）。每一条都来自本项目真实发生过的失败，
> 附触发条件、现象、定位方法与修复，并给出在本项目中的证据位置。
> 所有条目**不绑定题目本身**——换一个 FPGA 项目、换一块板卡仍然适用。

---

## 0. 这份技能包解决什么问题

嵌入式 FPGA 项目最容易浪费时间的不是「不会写 RTL」，而是**四类反复踩的坑**：

| 类别 | 典型表现 | 本包对应条目 |
|---|---|---|
| **面积类** | 单模块综合能过，整机放不下 | P1、P2、P3 |
| **接口类** | 单个通道能跑，多通道/多设备就死锁或退化 | P4、P5、P6 |
| **口径类** | 数字看起来有收益，实际是测量方式变了 | P7、P8、P9、P10 |
| **流程类** | 代码没错，但操作顺序让系统进入不可恢复状态 | P11、P12、P13、P14 |
| **判据类** | 指标看起来支持结论，其实指标的语义不对 | P15、P16、P17 |

使用方式：**开新项目时逐条对照**，把「本项目当前处于哪一条」写进设计文档。
### 配套的可运行脚本

`skill/tools/` 下有 **3 个独立可运行的校验脚本**，无需任何项目代码即可使用：

| 脚本 | 对应条目 | 作用 |
|---|---|---|
| `tools/numeric_compare.py` | P10 | 浮点/定点逐位比对，报逐位差异数、最大绝对差、最大 ULP 差 |
| `tools/check_route_report.py` | P1、P3 | 解析 Vivado 报告，判定阶段（综合/布局/布线）与资源时序是否通过 |
| `tools/acceptance_with_negative_control.py` | P14 | 逐字节验收 + **强制三种人工破坏的负对照**，负对照失败则拒绝出结论 |

三个脚本都只依赖 Python 3 标准库，且都用真实数据自测过。详见 `tools/README.md`。
失效条件写在每一条末尾——**不要把它当成永远成立的规则**。

## P1　单模块 OOC 综合面积不能直接相加到整机

**触发条件**：给现有系统新增一个 AXI 主设备或一个新数据通路，然后用该模块的独立综合报告
去推算「装得下吗」。

**现象**：模块单独综合 `4,466 LUT`，整机只增加 `74,339 − 65,624 = 8,715 LUT`，
**差 1.89 倍**。而且增长不止发生在新增模块本身：

| 模块 | 加之前 | 加之后 | 增量 |
|---|---:|---:|---:|
| 新增模块（CNN） | 0 | 5,202 | +5,202 |
| **既有 FSR** | 20,317 | 21,875 | **+1,558** |
| **既有 GPU** | 18,026 | 18,742 | **+716** |
| **既有 DDR4 控制器** | 7,647 | 8,046 | **+399** |
| **既有互联** | 9,710 | 10,001 | **+291** |
| DMA | 1,555 | 1,654 | +99 |
| **合计** | 65,502 | 73,767 | **+8,265** |

**根因**：新增一个 AXI 主端口会推高互联的仲裁/位宽/时序代价，进而迫使既有模块的
组合逻辑重新展开。OOC 只算「它自己」，不算「它带来的邻居」。

**定位方法**：新增模块后**必须**做一次整机 `opt_design` + `place_design`，
读 `utilization.rpt` 的 CLB LUT 总数与 `utilization_hier.rpt` 的逐模块增量。
只看模块报告会得出相反结论。

**修复**：预算时给新增模块乘 1.8–2.0 的集成系数；更稳妥的做法是**只认整机报告**。

**证据**：`build/minecraft-java-125/dual-tmu-cnn-banks24-r1/final_opt_utilization.rpt`
（LUT 74,339 / 70,560 = 105.36%，CLB 需 5,512 有 5,304 → `place_design` 失败）。

**失效条件**：若新增模块不引入新 AXI 主设备、不复用既有互联（例如纯片内 FIFO 旁挂），
集成系数会小很多。此时仍应以整机报告为准，但不必默认为 2 倍。

## P2　HLS 面积重建有下限，收敛不了就该换问题

**触发条件**：把一个通用 C++ 前端整体 HLS 化，然后逐轮做「共享运算单元、把状态搬进 RAM、
把列表换成索引」这类重构。

**现象**：连续 27 轮面积重构，从 `374,209 LUT` 一路降到 `139,017 LUT`（−62.8%），
但可用空间只有 `32,510 LUT`——**降了一半以上，差距仍是 4.3 倍**。

**根因**：这轮重构的共同思路是「把值换成下标」（不再传 84 字节顶点视图、
120 字节静态参数、整块裁剪列表，只传银行号）。这是对的，也确实砍掉一半面积；
但剩下的面积里，**算法本身的并行度**（6 个裁剪面 × 2 套 TMU 梯度 × 任意图元模式）
无法靠换下标消除。

**定位方法**：做两轮「特别乐观的减法」自检——
把变换、裁剪、法线矩阵三部分**全部假设成零面积**，看还剩多少。
本例剩余 `46,058 LUT`，仍超 32,510。这一步能在第 3 轮就终止无效重构，而不是第 27 轮。

**修复**：面积不收敛时，改变的是**问题边界**（少硬化几个阶段、只硬化无裁剪无光照批次），
而不是继续重构同一个全功能核。

**证据**：`docs/JavaMC_完整几何前端_容量与吞吐可行性复核_20261030.md:84-87`。

**失效条件**：若目标器件余量在 10 万 LUT 以上，同样的重构可能就收敛了。
「有下限」是针对**小器件 + 全功能**这个组合，不是针对重构本身。

## P3　`place_design` 失败时，任何时序数字都不存在

**触发条件**：报告里出现「WNS +0.741 ns 达标」就以为时序没问题。

**现象**：同一份报告里 `WNS +0.741 ns`（看起来很好）但 `WHS −0.110 ns`（保持违例），
而**布局根本没成功**——没有布线，没有最终时序，没有位流。

**根因**：`opt_design` 之后的时序是**布局前估计**，互连线延迟还是统计模型。
布局失败时，这份估计的物理意义很弱；保持时间在布局前就违例尤其危险，
因为真实布线只会更差。

**定位方法**：区分三个阶段的报告——
① `synth`（综合，最乐观）② `opt_design` 后（布局前估计）③ **`route_design` 后（唯一可信）**。
只有第 ③ 份才能写进文档。

**修复**：面积/时序结论一律标注阶段。若只有 ① 或 ②，明确写「估计值，非布线结果」。

**证据**：同 P1 的 `final_opt_timing.rpt` 与 `final_opt_hold_timing.rpt`。

**失效条件**：小规模模块（占用 < 10%）的布局前估计通常与布线后接近，
但仍不能替代布线后数据。

## P4　DMA「槽数」不等于「并发数」

**触发条件**：看到 8 个 1 MiB 缓冲槽，就以为可以同时飞 8 笔传输。

**现象**：8 个槽提供了**生命周期与准备空间**，但驱动与连接器都限制**每通道一笔在途**。
每次提交前都要 `waitForDma()` 等上一笔完成。8 槽不会变成 8 倍吞吐。

**根因**：`dmaengine_prep_slave_single` + 单一 completion 的设计下，通道是串行的。
槽的价值在于「CPU 可以先写另一个槽」，不是「硬件并行搬运」。

**定位方法**：读驱动里 `c->active` 的检查，以及用户态 `waitForDma()` 的调用点数量。
本例：`rix_dma_proxy.c:48 if(c->active) return -EBUSY;`。

**修复**：要么接受串行（并据此做预算），要么改驱动为多描述符队列（代价是回调与
错误处理复杂化）。**不要靠「多加几个槽」来提速**。

**证据**：`linux/dma-proxy/rix_dma_proxy.c:44-62`、`src/ps/DMAProxyBusConnector.cpp:66-74`。

**失效条件**：若驱动改为多 in-flight 描述符队列，此条不成立；届时仍需实测确认
DDR 与互联能否支撑并发。

## P5　跨时钟域要用「打包 + 握手」，不能只用两级触发器

**触发条件**：把多比特状态（槽号 + 帧号）用两级同步器送过时钟域。

**现象**：单个 bit 用 2FF 是对的，但**多比特同时跳变**会采到「新旧混合值」，
表现为偶发错帧、错槽，且抓不到规律。

**根因**：2FF 只保证每个 bit 单独稳定，不保证 bit 之间同拍。

**定位方法**：`report_cdc` 里出现「Multi-bit CDC」类告警；
或现象表现为「大部分时候正常，几百分之一错一次」。

**修复**：三条可用结构——
① **req/ack 翻转 + held 总线**（本项目 `rix_snapshot_cdc`，1024 周期节流，翻转率极低）；
② **bundled data + toggle**，接收侧只在安全窗口采样（本项目 `rix_presenter`，只在
`vs` 消隐且扫描空闲时接收）；
③ 格雷码（仅适用于单步递增的计数器）。

**约束**：`set_false_path` 只对同步器**首级**；对 held 总线要用
`set_max_delay -datapath_only` + `set_bus_skew`，否则工具会按普通路径优化掉延迟。

**证据**：`config/rasterix_cdc.xdc:3-10`、`src/rtl/video/rix_presenter.v:39-42`、
`src/rtl/common/rix_snapshot_cdc.v:9-30`。

**失效条件**：纯控制脉冲（单 bit 事件）用 2FF 即可，不需要打包。

## P6　复位要「异步置位、同步释放」，且每域独立一条链

**触发条件**：一个复位信号同时驱动三个时钟域的所有寄存器。

**现象**：综合能过，仿真能过，上板偶发首帧错乱或启动挂死；`report_cdc` 出现复位路径告警。

**根因**：复位的**释放沿**若在某个域的时钟沿附近，不同寄存器会在不同拍退出复位。
置位不需要同步（异步有效），**释放必须同步**。

**修复**：每个时钟域一条独立的 4 级 `ASYNC_REG` 链，末级寄存输出；
对链的 `CLR` 脚加 `set_false_path`（置位是异步的，不该被当数据路径分析）。
若一个域依赖另一个域的「就绪」（如 MIG 校准完成、MMCM 锁定），把这些就绪信号
也纳入同一条链，避免两条独立链在末端重汇合。

**证据**：`src/rtl/common/rix_domain_reset.v:14-38`、`config/rasterix_reset_cdc.xdc:4-6`。

**失效条件**：单一全局复位且全设计只有一个时钟时，不需要多链。

## P7　「利用率」类计数器极容易读错

**触发条件**：看到计数器显示「非空闲 48.9–51.9%」，得出「GPU 只用了一半，可以翻倍」的结论。

**现象**：那个计数器是 `assign perfBusy = state != COMMAND_IN;`——**命令解析器不在接收状态**
的累计时间。它包含「解析命令」「等待下游」「协议空泡」全部状态，
**不是「像素管线正在有效着色」**。

**根因**：为了省面积，最初只暴露了一个粗粒度状态信号；后续被当成了利用率。

**定位方法**：读计数器的定义那一行源码，而不是读它的名字。若定义是
`state != X`、`busy = !idle`、`active = valid && ready` 这类，先问「它到底排除了什么」。

**修复**：把真正的通路指标单独计数——输入 `TVALID && !TREADY`（上游供不上）、
`!TVALID && TREADY`（下游空转）、有效片元数、光栅反压周期。
**没有这三个计数器之前，任何「加速了」的归因都不成立。**

**证据**：`external/RasterIX/rtl/RasterIX/CommandParser.v:127`；
`docs/JAVA125_COMMAND_STAGING_2026-10-28.md:75,79`。

**失效条件**：若计数器直接来自「有效字节数 / 时钟数」这类物理量，可以直接用。

## P8　性能数字必须带口径，且口径要写进同一行

**触发条件**：文档里出现「57 FPS」「44 FPS」「40 FPS」这类裸数字。

**现象**：同一项目里 5 个「FPS」其实测的是五件事：

| 数字 | 真是什么 |
|---|---|
| 57.09 | **超分新输出帧率**（ClassiCube 线，120 秒长测） |
| 44.35 | **命令重放上限**（驻留纹理、3 帧、无游戏逻辑） |
| 40.76 | Mali 的 **PBuffer/X11 完成交换**，不是 LCD 通路 |
| 25.72 | 游戏**完成帧率**（静止 Tiny 短测） |
| 60.125 | **LCD 扫描节拍**，与新帧无关 |

**再补两个最容易越界的数字**：

| 数字 | 真是什么 | 为什么不能当成绩 |
|---|---|---|
| **44.35** | 命令重放**上限**（驻留纹理、3 帧、无游戏逻辑） | 省掉了游戏逻辑与几何计算，**不是游戏帧率，也不是硬性上限** |
| **40.76** | Mali 的 PBuffer/X11 完成交换 | **不是 LCD 通路**，与本作品路线不同 |

本项目在文档里明确写了一条禁令：
「**不要把 44.35 当游戏帧率，不要把 40.76 当本路线成绩，不要承诺稳定 60。**」

**根因**：不同阶段用不同工具测量，最后拼在一张表里。

**修复**：建三条硬规矩——
① 每个数字后必须跟一句「测什么」；② **源帧率 / 增强完成帧率 / 扫描频率三者分开记**；
③ 单点值必须给区间或 session 标识（本项目同一配置三次 session 是 24.94 / 25.38 / 25.72，
**波动 3% 大于多数「优化」的组间差**）。

**证据**：`docs/前端与架构全景_20261030.md` §7.3。

**失效条件**：无。这条对任何性能文档都成立。

## P9　配置键写错会让整组实验白做

**触发条件**：测试脚本用 JSON 写游戏配置，字段名靠记忆或参考旧版。

**现象**：四轮 ABBA、48 张原生图、完整验收全部通过——但后来逐字核对才发现，
脚本写的是 `renderDistance`，而这款游戏读的是 `viewDistance`。
**那组数据对应的是完全不同的视距**，所有「收益」失去意义。

**根因**：配置文件「写进去了」不等于「生效了」。游戏忽略未知键且不报错。

**定位方法**：不要从配置文件推断生效值，**从游戏对象读取实际值**，
并且在暖机开始、计数开始、结束时各读一次，三次必须一致。

**修复**：所有性能结论附带「实际生效设置」快照（本项目后来固定为十二项运行时检查）。

**证据**：`docs/MALI_JAVA125_2026-10-28.md:24`（R75–R78 的 Tiny 标注作废，实为 Far）。

**失效条件**：无。

## P10　浮点运算重排会改变结果，必须量化而不是假定

**触发条件**：为了省一次矩阵乘法，把 `projection.transform(modelView.transform(v))`
改为预乘矩阵 `M = projection * modelView` 后一次变换。

**现象**：数学上等价，但 float32 下有 **47.08% 的坐标字段逐位不同**，
最大绝对差 `3.576e-7`，最大 **ULP 差 1,144**（10,683 / 11,520 个顶点受影响）。

**根因**：矩阵先乘再变换改变了加法分组顺序；浮点加法不满足结合律。

**定位方法**：写一个**逐位探针**——用真实夹具输入，分别走旧路径与新路径，
每步运算后舍入到 float32，比较逐位结果、最大绝对差与最大 ULP 差。
本项目脚本：`tmp/mvp_float_probe.py`。

**修复**：不要看「最大绝对差很小」就放行。判据应该是**下游是否对逐位敏感**
（如定点化、边界裁剪、深度比较）。若敏感，就保留原运算顺序。

**附带教训**：做这个变换时还要注意**行向量 vs 列向量约定**。
本项目 `Mat44::transform` 按行向量计算，正确合成顺序是 `modelView * projection`，
写成 `projection * modelView` 会**倒置顺序**——这是我在需求里写错的，被模型指出来了。

**证据**：`docs/JAVA125_CPU_OPTIMIZATIONS_2026-11-01.md`（MVP 探针表）。

**失效条件**：若下游全程 float64 且只做「大于/小于」判断，ULP 差异可能可接受；
但仍需实测，不能假定。

## P11　串口/设备句柄是独占资源，一个进程占住就全线阻塞

**触发条件**：上位机脚本已经打开串口，或板上某个进程持有设备句柄。

**现象**（三种都真实发生过）：
① 上位机 `SerialPort.Open()` 抛 `Access to the port 'COM11' is denied`；
② 板上新加的启动器**一直持有状态查询设备的句柄**，内核因此拒绝卸载显示驱动，
    保护检查在修改 PL 之前就拦住了操作；
③ 上传尚未结束就提前打开串口，后两步被占用保护拒绝。

**根因**：串口与 misc 设备都是独占的；`open()` 成功后不 `close()` 就一直锁着。

**定位方法**：报 `Access denied` 时先查「谁占着」，不要重试。
Windows 侧看是否有 `~$` 类锁文件或残留进程；Linux 侧 `fuser /dev/xxx`。

**修复**：**读取后立即关闭句柄**（本项目把「读状态」改成 open→read→close 三步，
不再常驻持有）；上位机脚本每步操作串行化，等上一步 ack 再开下一步。

**证据**：`docs/GAME_LAUNCHER_SESSION_V3_2026-11-01.md`（启动器持句柄导致卸驱动失败）。

**失效条件**：需要持续轮询的场景（如每秒采样）可以常驻，但要在结束路径保证关闭，
且不能与需要独占的其他操作并发。

## P12　一次「不安全终止」会让整板进入不可继续状态

**触发条件**：测试中强杀游戏进程，或 DMA 超时后继续操作。

**现象**：系统写入一个隔离标记（同一 `boot_id` 内有效），此后**任何新游戏进程启动都被拒绝**，
提示「Previous GPU/DMA failure in this boot; reboot the board before starting another game」。
一轮试验就此报废，必须整板重启并重建 RAM 环境（本项目要重传 JRE/素材/库，约 10–20 分钟）。

**根因**：DMA 超时可能让 GPU 停在半完成状态而显示计数器仍显示 ready。
与其猜，不如强制重启。这是**刻意的设计**，不是 bug。

**定位方法**：看隔离文件是否存在且 `boot_id` 与当前一致。

**修复**：所有会改硬件状态的操作遵循「持锁 → 查隔离 → 快照 → **先构造反向回滚包** →
改 → 验证 → 恢复」的顺序。**回滚包必须在改动之前就准备好**，
否则失败时没有可用的反向路径。

**证据**：`linux/game_runtime_support.py:18-37`、`linux/java_minecraft/run_java256_trial.py:77-88`。

**失效条件**：纯只读操作不受此限（但仍建议持锁，避免与写操作并发）。

## P13　位流「RAM 加载」意味着断电即回旧版本

**触发条件**：通过 FPGA manager 从 RAM 加载新位流做试验，然后认为「已经部署了」。

**现象**：一切正常，但**断电重启后回到 SD 里的旧位流**。而且**没有任何脚本会检测这件事**
——因为 SD 的 `BOOT.BIN` 里的 PL 分区与 RAM 加载的位流不是同一份，
也没有绑定校验。

**根因**：RAM 加载只改 FPGA 配置寄存器，不写 SD。

**定位方法**：分别核对三个身份——
① RAM 当前位流的 SHA（从 receipt 文件读）；
② SD 上 `BOOT.BIN` 的 SHA；
③ `release_manifest` 里记录的 PL 分区来源。
三者不一致时，说明「板上跑的不是开机加载的那份」。

**修复**：试验阶段显式标注「RAM only，断电丢失」；
要真正落地必须更新 SD 并在**冷启动**后重新验证身份。

**证据**：`docs/前端与架构全景_20261030.md` §7.1 第 6 条；
`report/minecraft-java-125/swap-fence/r131-board/result.json:249`（`firmware_path=/tmp/...`）。

**失效条件**：若位流已写入 SD 的 `BOOT.BIN` 且经过冷启动验证，此条不适用。

## P14　验收脚本本身会是最大的假失败源

**触发条件**：连续几轮「验收失败」，但游戏跑得好好的。

**现象**（两条真实记录）：
① 验收器把**显示模式与双缓冲 bank 位一起比较**，导致 `bank 1` 的正常值 `0x203`
    被误判为异常，报「快照已过期」——**其实快照没过期**；
② 验收器把「单行汇总统计」误当成「多行时间序列」，拒绝了实际处理了 1.07 亿顶点的正常结果。

**根因**：验收器是对**历史某一次输出格式**写的，格式演进后判据没跟着改。

**定位方法**：验收失败时，**先手工核对一次原始数据**，确认是「真失败」还是「判据过期」。
区分方法：把断言拆成「结构断言」（字段存在、类型对）与「值断言」（等于某个期望），
逐个单独跑。

**修复**：断言要写「校验什么、为什么是这个值」，并附一个**负对照**
（故意构造错误输入，确认验收器真的会报错）。

**证据**：`docs/CNN_STYLE_V7_2026-11-02.md` 相关轮次；
`docs/CLAIM` 见 `docs/JAVA125_CPU_OPTIMIZATIONS_2026-11-01.md` 的 93 用例 + 负对照 85 差异。

**失效条件**：无。任何自动化验收都需要负对照。

## P15　FPGA 寄存器映射要留「能力寄存器」，不要靠崩了才发现

**触发条件**：PL 侧功能版本会变（有的位流带 CNN、有的不带；有的带完整超分、有的只有双线性），
但软件侧的探测方式是「调用一下看看」，或者干脆假定功能一定存在。

**现象**：换一个位流之后，软件仍然尝试访问不存在的 IP。要么 AXI 读回全 `0xFFFFFFFF`、
要么总线挂死、要么拿到全零数据被当成合法结果继续算。**最坏的情况是「不报错但结果全错」。**

**根因**：缺少一个「本版本有什么 / 没有什么」的**显式声明**。
硬件的存在性靠「能不能访问成功」来推断，而访问失败在很多 AXI 场景下**不产生错误信号**。

**定位方法**：换位流后，先读能力寄存器并与软件预期比对；不一致就必须拒绝继续。

**修复**：在 CSR 空间里划出一组**只读能力寄存器**，每个 bit 或每个字节声明一项能力：

```verilog
// rix_java_cnn_unavailable.sv —— 把「没有 CNN」这件事做成可读的常量
// 读任何寄存器都返回 0：shape / capabilities / ABI / ready 全部为「不存在」
always_comb begin
  case (s_axi_araddr[...])
    ...
    default: s_axi_rdata = 0;   // 而不是返回 0xFF 或挂死
  endcase
end
// 文件头注释即契约：capability = 0 表示本版本没有 CNN 引擎
```

本项目实例：Java 双 TMU 位流里，CNN 模块被例化为一个 **stub**
（`rix_java_cnn_unavailable.sv`），能力位恒为 0，因此软件**在改硬件之前**就知道不能调用，
而不是访问到空地址后崩掉。

**为什么这条值得进技能包**：
它把「功能是否存在」从**运行时试探**变成**静态契约**。
换任何 FPGA 项目、任何接口（PCIe、AXI、APB）都成立。

**失效条件**：
- 若软件与位流**永远同版本同批次发布**、不可能错配，这条的收益很小。
- 能力寄存器本身也必须被正确约束（只读、无复位歧义），否则它会成为新的不确定性来源。
## P16　缓存命中率高，不等于端到端更快

**触发条件**：给一个热点加缓存（位置复用、索引缓存、纹理缓存），
然后用**命中率**证明这个优化有效。

**现象**：命中率 **70.18%**，看起来很成功；但同一轮 ABBA 对照的端到端帧率是
**24.42 → 25.17，即 −2.99%**。**命中率越高，反而越慢。**

**根因**：命中率只统计「查到了」，不统计 **查找本身的代价**：

- 缓存键的比较（本例是 128 槽 → 需要精确键匹配）
- 命中后仍要读写缓存条目
- 未命中路径多了一层判断
- 缓存的插入/淘汰可能打断流水

当**单次查找的成本 × 查找次数 > 省下的计算成本**时，命中率再高也是净亏。

**定位方法**：

1. 先测「加缓存前」的单次计算成本
2. 再测「查找 + 命中读写」的单次成本
3. 用 `命中率 × 省下成本` 与 `查找次数 × 查找成本` 比较，看是否真为净收益
4. **最终只认端到端帧率**，命中率只作为解释性指标

本项目的原话记录：「缓存查找、精确键比较及结果读写自身有成本；本次实验没有把这些成本与场景差异独立分解，
**不能只凭命中率就断言计算时间减少了 70%**。」

**修复**：命中率是**必要不充分**指标。若端到端无收益，就应该撤掉缓存而不是继续调命中率。

**证据**：`docs/JAVA125_BUFFER_POSITION_OPTIMIZATION_2026-10-28.md:42-44`
（128 槽位置复用，命中 70.1761%，FPS 24.4162 vs 25.1691）。

**失效条件**：
若「查找成本」可以被硬件并行掉（如 CAM 全并行比较、TLB 式单拍命中），
命中率与端到端收益的正相关性会显著提高。但仍需实测，不能假定。

## P17　省下资源不等于提速：先确认哪个资源真正在约束

**触发条件**：看到某个模块占比高，就把它精简掉，然后认为「省了 LUT 应该更快」。

**现象**：AXI 互联精简掉 **6,059 LUT / 8,975 FF**（65,624 → 59,565），
时序还更宽松了（全局 WNS +0.105 ns）；但游戏帧率 **−13.5%**（26.35 → 22.79）。

**根因**：省下来的 LUT 是**拿带宽换的**。这条链路当时的瓶颈就在**带宽**，不在面积。

本项目的判断依据：**AXI 互联比 GPU 本体还大 36%**，而且互联的 LUT 主要是
数据位宽、缓冲深度与仲裁逻辑——**削它就是在削并发能力**。

**定位方法**：动手前先回答一个问题——**「这个设计现在被什么约束？」**

| 约束类型 | 判据 | 精简该模块的后果 |
|---|---|---|
| **面积** | 布局失败 / LUT 超容量 | 可能提速（如果同时没伤到通路） |
| **带宽** | 实测吞吐 < 链路理论值，且有反压 | **变慢** |
| **延迟** | 关键路径 WNS 为负 | 可能提速 |
| **存储** | BRAM 满 | 与速度无关 |

本项目的互联精简属于第二类，所以「省了 6,059 LUT」换来的是 −13.5%。

**修复**：面积优化与带宽优化是**两个方向**。若瓶颈是带宽，正确做法是加宽/加深，
而不是精简。**资源节省必须与「哪个资源是瓶颈」一起判断。**

**证据**：`docs/JAVA125_INTERCONNECT_REPLAY_2026-10-28.md:24`（资源表）、
`docs/frontend-architecture-panorama_20261030.md:447`（「互联比 GPU 大 36%」）。

**失效条件**：
若该模块同时是面积和带宽的约束点，精简可能两边都伤，此时应换架构而不是调参。
若器件有充足带宽余量（如实测链路利用率 < 30%），精简面积通常无害。
